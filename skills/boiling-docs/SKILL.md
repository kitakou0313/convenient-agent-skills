# Boiling Docs — 文書全体を内容を削らずに読みやすく書き直す（修正役・自律ループ）

入力された文書（形態は問わない）を、内容を削らずに読みやすく書き直し、元の文章に反映するスキル。
**文書の評価は `boiling-docs-core` スキルを使った独立した評価役が担当する。** このスキルを使うメインエージェントは、
評価役が指摘した違反を直す修正役である。修正と評価を、基準を満たすまで自律的に繰り返す。

- 評価の基準と出力の形は、`boiling-docs-core` が定める。このスキルは基準の中身を持たない
- 違反の直し方は、このスキルでは定めない。修正役が、指摘された違反と基準から判断する
- 評価役は非対話・ステートレスで、呼び出しごとに渡された入力だけから判定する

## 全体の流れ

1. **入力の受け取りとソース判定**（ユーザーとの対話）— 対象文書・想定読者を受け取り、取得元を判定する
2. **計画の提示と承認**（ユーザーとの対話）— 想定読者・評価基準・終了条件・作業版の保存先を提示し、承認を得る
3. **事前準備**（Coding Agentが実施）— 作業版の書き込みと評価役の起動に必要な権限を、前倒しで確認する
4. **ループの実行**（Coding Agentが自律実行）— 修正→評価→判定を、終了条件まで繰り返す
5. **最終レビューと反映**（ユーザーとの対話）— 最終稿のレビューを受け、承認後に元の文章へ反映する

## Phase 1: 入力の受け取りとソース判定

- 対象文書をユーザーから受け取る。未指定の場合は確認する
- **想定読者**を決める
    - ユーザーが依頼文の中で述べている場合は、それを使う
    - 述べていない場合は、文書の分野・文体・既出の語から推定する。推定した読者像と根拠は、Phase 2で提示して確認する
    - ここで決めた想定読者は、以降の評価でずっと固定して使う（評価のたびに推定し直さない）
- 取得元を判定し、Phase 5の反映方法決定のために記録しておく:
    - **ファイル**: ローカルファイルパスが指定された場合。パスを記録し、内容を読み込む
    - **MCPリソース**: MCPツール経由（Google Drive/Docs、Gmail等）で取得した場合。使用したMCPサーバー名を記録し、
      対応する編集用toolの有無をこの時点で確認しておく
    - **テキスト**: チャットへの直接貼り付け、または上記いずれにも該当しない場合。反映先を持たない
- 判定が曖昧な場合は決め打ちせず、ユーザーに確認する

## Phase 2: 計画の提示と承認

次の内容をユーザーに提示し、明示的な承認を得てからPhase 3に進む（承認前にPhase 4を開始しない）。

- **想定読者**: 推定した場合は、その旨と根拠を添える。ユーザーが修正した場合は、修正後の読者像を固定する
- **評価基準**: 評価役が判定する8項目の名前と、保全チェック（原文の内容が欠落していないかを見る関門）がある旨。
  基準の詳細は評価役の定義に従う
    - 非記号的な読みやすさ: 依存順／結論の先頭明記／用語の事前定義
    - 記号的な読みやすさ: 表記ゆらぎ／単文／文の長さ／箇条書きの構造／番号付き手順
- **ループの内容**: 修正→評価→判定を自律的に繰り返す。ユーザーに確認するのは、終了後の最終レビューだけである
- **修正役の制約**: 原文の内容は削除しない。追加できるのは、定義と具体例だけである
- **終了条件**: Phase 4の終了条件を提示する。上限は5回である
- **作業版の保存先**: 「作業版のファイル命名規則」に従って決めた保存先。MCPリソースまたはテキストが元の場合は、保存先を
  ユーザーに確認する
- **必要な権限**: 作業版ファイルの書き込み、評価役の起動

## Phase 3: 事前準備

Phase 2で承認された計画をもとに、ループが承認待ちで中断しないよう、作業版ファイルの書き込みと評価役の起動を
一度実行（または安全な形で試行）して、事前に承認を得ておく。

## 作業版のファイル命名規則

各イテレーションでどのような変更が加わったかを比較できるように、イテレーションごとに作業版を別ファイルとして保存する。
直前の版は上書きしない。

- ベース名は、元がファイルの場合はそのファイル名、それ以外の場合はユーザーと確認した名前とする
- 保存先は、ベース名の拡張子の直前に `-loop{N}`（Nは1始まりの通し番号）を付けたファイル名とする
  （例: `foo.md` の1回目は `foo-loop1.md`、2回目は `foo-loop2.md`）
- すべての作業版は、ループ終了後も削除せず残す
- 保存先に同名のファイルが既にある場合は、上書きしてよいかユーザーに確認する

## Phase 4: ループの実行

ループ実行中は、ユーザーの確認を求めずに自律的に処理し続ける。

### 4-1. 初回評価

原文を評価役に渡して評価する（評価の渡し方は4-3に従う）。初回評価は、イテレーションの回数に数えない。

- 総合が `合格` なら、修正は不要である。ループに入らず、Phase 5へ進む
- `不合格` なら、4-2へ進む

### 4-2. 修正

直前の評価で `不合格` だった項目の違反箇所を、基準を満たすように修正する。直し方は、指摘と基準から判断する。

- 1回目は原文を土台に、2回目以降は直前の作業版を土台にする。結果は、新しい作業版のファイルとして保存する
- 原文の内容は**削除しない**。追加できるのは、定義と具体例だけである
    - 定義の出どころは、原文にある定義か、広く確立した一般知識（公的な規格・標準的な技術用語など）に限る
    - 原文に定義がなく、文書固有の語（社内用語・独自の略語・プロジェクト名など）は、定義を作文しない
- 保全チェックが `不合格` なら、欠落した原文の箇所を作業版に戻す
- すでに `合格` の項目を壊さない
- 原文の言い回しは、基準を満たすために必要な範囲を超えて変えない
- **修正不能の申告**: 修正役が補えない定義不足（`用語の事前定義` の違反）は、語ごとに理由を添えて「修正不能」と申告できる
    - 申告できるのは、定義不足だけである。ほかの項目の違反は申告できない
    - 申告した語は、以降の修正の対象から外す。以降の評価で同じ指摘が返っても、申告済みとして扱う

### 4-3. 評価

直前に保存した作業版を、評価役に渡して評価する。評価役には、次の3つだけを渡す。

- **対象文書**: 今回の作業版の本文（ファイルの内容）
- **想定読者**: Phase 1で固定した想定読者
- **原文**: 保全チェックのための、修正前の文書

どう修正したか、前回の評価結果、修正不能の申告は、**渡さない**（評価役を独立に保つため）。

評価役には、サブエージェント・別プロセス・別セッションなど、独立した実行手段を使う。そのような手段がない環境では、
修正の文脈を含まない評価専用のプロンプトを新たに組み立てて評価させる。

`boiling-docs-core` スキルを名前で起動できない環境では、`boiling-docs-core/SKILL.md` を探して読み、その手順に従って
評価させる。`boiling-docs-core` が見つからない場合は、処理を行わず、「`boiling-docs-core` が導入されていないため実行
できない」ことをユーザーに伝えて中断する（元の文章は変更しない）。

評価役の応答から `<evaluation>` ブロックを取り出して保持する。ブロックが取り出せない場合は、1回だけ再評価する。
それでも取り出せなければ、ユーザーに報告して中断する（元の文章は変更しない）。

### 4-4. 判定

次の終了条件のいずれかを満たせば、ループを終了してPhase 5へ進む。

1. **全項目が合格**: `総合` が `合格` である
2. **残りがすべて修正不能の申告済み**: `不合格` の項目が `用語の事前定義` だけで、その違反がすべて申告済みの語である
   （保全チェックを含め、ほかの項目は `合格` か `該当なし`）
3. **上限に到達**: 修正→評価のイテレーションを5回行った。合否にかかわらず終了する

終了条件を満たさなければ、評価結果の違反を土台に、次のイテレーション（4-2）に進む。

各イテレーションの終わりに、「イテレーション番号 / 不合格の項目 / 生成した作業版のパス」を、1〜2行でユーザーに
報告する。

## Phase 5: 最終レビューと反映

### 5-1. 最終レビュー

ユーザーに、次の内容を提示してレビューを依頼する。

- 最終版の作業版のパスと本文
- 終了した理由（終了条件の1〜3のどれか）
- 残っている違反（`不合格` の項目と違反箇所）
- 修正不能の申告の一覧（語と理由）
- 各イテレーションの作業版を残しており、比較できること

承認が得られたら、5-2へ進む。却下・修正依頼があれば、要望を修正役への追加指示としてPhase 4に戻る。

- 最終版を土台に、修正→評価のループを再実行する。イテレーションの回数は、5回として数え直す
- 作業版の番号は通し番号で続ける。既存の作業版は上書きしない
- 保全チェックは、引き続き原文に対して行う
- 評価役には、ユーザーの追加指示を渡さない。追加指示が評価基準と衝突し、同じ指摘が返り続ける場合は、衝突している
  指摘を「ユーザー要望による例外」として扱う。終了条件2の判定で、修正不能の申告と同じように扱う。最終レビューで、
  例外として扱った指摘を報告する
- 承認されるまで、5-1を反復する

### 5-2. 元の文章への反映

Phase 1で判定したソース種別に応じて反映する:

- **ファイル** → ファイル編集機能でそのファイルを直接編集する
- **MCPリソース** → 対応するMCPサーバーの編集用toolで反映する。編集用toolが見つからない、または権限がない場合は
  実行せず、代替手段（手動反映・テキスト出力への切り替え等）をユーザーに確認する
- **テキスト** → 反映先が無いため、最終文章をチャットに出力するのみ

反映後、変更箇所・反映先を簡潔に報告する。

## エッジケース対応

- **`boiling-docs-core` が見つからない**: 処理を行わず、導入が必要であることをユーザーに伝えて中断する
- **評価役の応答が `<evaluation>` ブロックの形式を満たさない**: 1回だけ再評価し、それでも満たさなければユーザーに報告して
  中断する。元の文章は変更しない
- **初回評価で総合が合格**: 修正せず、元の文章も変更せずに、その旨を報告する
- **文章が長大**: 評価役には、常に文書の全文を渡す。修正は、章・セクション単位で行ってよい
- **原文の内容の削除をユーザーが求めた場合**: このスキルは内容を削除しないため、対象外であることを伝える
- **MCPリソース由来だが対応する編集toolが無い/権限が無い場合**: 反映を実行せず代替手段を確認する
- **Phase 2の承認前**: ループを開始しない
- **Phase 5の承認前**: 元の文章への破壊的操作（上書き）を行わない
