# INVEST Task Splitter — 要件をINVESTを満たすタスクに分割する

渡された要件を、[INVEST](https://ja.wikipedia.org/wiki/INVEST)の原則を満たす粒度のサブタスクに分割し、
ユーザーに提示する前に独立した検証者でその充足を確認・修正するスキル。分割結果は、他者への依頼や
ブロッキングの有無、見積もりの確度に応じた3段階の優先順位（着手順）とあわせて提示する。

## 全体の流れ

1. **要件の受け取り**（ユーザーとの対話）— 分割対象の要件を確認する
2. **おおまかな実施事項のヒアリング**（ユーザーとの対話）— ユーザー自身の暗黙的な認識を明示化する
3. **INVESTを満たす分割**（Agentが実施）— ヒアリング結果を、再帰的に分割してINVESTの粒度に落とし込む
4. **検証・修正ループ**（Agentが実施）— 独立した検証者がINVEST充足と網羅性を判定し、不合格なら該当タスクを修正して再検証する
5. **優先順位付け**（Agentが実施）— 各タスクをTier1/2/3に分類し、着手優先度として並べる
6. **提示**（Agentが実施）— 結果をユーザーに提示する。希望があればMarkdown保存も行う

## INVESTとは

このスキル内で以下の6項目として独立して用いる（定義は
[INVEST(Wikipedia)](https://ja.wikipedia.org/wiki/INVEST)の考え方に基づく）。

- **Independent（独立）**: 他のタスクへの依存を最小限に抑え、単独で着手・完了できる
- **Negotiable（交渉可能）**: 実装の詳細まで固定されておらず、進め方に調整の余地が残っている
- **Valuable（価値がある）**: そのタスク単体の完了が、要件の達成に対して意味のある価値をもたらす
- **Estimable（見積もり可能）**: 作業量をおおよそ見積もれるだけの情報が記述されている
- **Small（小さい）**: 短期間で完了できる十分小さい単位である
- **Testable（テスト可能）**: 完了したかどうかを明確な基準で判定できる

## Phase 1: 要件の受け取り

- ユーザーから分割対象の要件を受け取る。チャット上の自由記述、またはファイルパス/Issue・チケットURLの
  指定を受け付ける
  - URL/ファイルが指定された場合、利用可能なツール（Web取得、`gh`コマンド等）で内容の取得を試みる。
    取得できない場合はその旨を伝え、ユーザーに内容の貼り付けを依頼する
- 要件が曖昧・抽象的な場合は、分割に着手する前に深掘りして具体化する（対象範囲、完了の定義、制約等）。
  依頼内容から自明な点は確認のみに留める

## Phase 2: おおまかな実施事項のヒアリング

Phase 3で自動分割する前に、ユーザー自身の暗黙的な理解を明示化し、Phase 5のTier1判定の材料にする。

- 「この要件を実現するために、大まかに何をする必要があるか」を白紙の自由記述で列挙してもらう
  （Agentから候補のたたき台は提示せず、ユーザー自身に挙げてもらう）
- 列挙された各項目について、以下2点を確認する
  1. **他者への依頼予定があるか**（yes/no/不明）
  2. **他のタスクの前提になる（ブロックする）と分かっているか**（yes/no/不明）
- 「不明」の回答は、Tier1の判定材料としては扱わない（Phase 5のAgent自身の依存関係分析による補完に委ねる）

## Phase 3: INVESTを満たす分割

Phase 2で得た各項目を、以下の手順でINVESTの粒度に分割する。

### 3-1. 初期分割

各項目について、単独でValuable・Testableとみなせる単位まで分割する。

### 3-2. 再帰的な粒度調整（Small基準）

分割した各タスクについて、Smallを満たすか（短期間で完結する十分小さい単位か）を判定する。満たさない
場合はさらに分割する。

- **深さ上限**: 最大3段階まで（Phase 2の項目を1段階目として数える）
- **分割停止基準**: これ以上分割すると、個々のタスクが単独でTestableまたはValuableを維持できなく
  なる境界に達したら分割を止める
- 深さ上限に達してもSmallを満たさない場合は、分割を止めて「これ以上機械的に分割していない（大きい
  可能性がある）」旨をそのタスクに明記する

### 3-3. 依存関係・委譲フラグの引き継ぎ判定

Phase 2でユーザーが「他者への依頼予定」「ブロッキング」とフラグを付けた項目が複数のサブタスクに
分割された場合、そのフラグを一律に継承せず、どのサブタスクが実際に該当するかをAgentが判断し直す。

## Phase 4: 検証・修正ループ

Phase 3で作成したサブタスク一覧を、ユーザーに提示する前に独立した検証者に判定させる。

### 4-1. 検証者の起動

ツールがサブエージェント・別プロセス・別セッションなど独立した実行手段を提供している場合はそれを
使う。そのような手段がない場合は、実装の文脈（どう分割したか、なぜその粒度にしたか）を一切含まない
検証専用のプロンプトを新たに組み立てて評価させることで代替する。

検証者に渡す情報は以下のみとする（Tier情報・分割の意図や理由は渡さない）。

- 元の要件（Phase 1で確定した内容）
- 提案されたサブタスク一覧（タイトル・説明のみ）
- 判定基準（後述の「検証者への指示」）

### 4-2. 検証範囲

検証者は以下を判定する。

1. 各サブタスクがINVESTの6項目を満たすか（満たさない項目があれば具体的に指摘する）
2. サブタスク全体が元の要件を過不足なくカバーしているか（網羅性のギャップ、および内容が重複する
   タスクの有無）

Tier分類（Phase 5）の妥当性は検証対象に含めない。

### 4-3. 判定と修正

- **全て合格** → Phase 5へ進む
- **一部不合格** → 指摘された該当タスクのみを修正する（合格しているタスクは変更しない）。網羅性の
  ギャップが指摘された場合は、不足分を埋める新規タスクをAgentが追加する。重複が指摘された場合は
  統合・削除する。修正後、4-1に戻り再検証する
- **修正回数が上限（5回）に到達** → ループを打ち切り、その時点のサブタスク一覧と、検証者が残した
  未解決の指摘をそのままPhase 5以降に引き継ぐ（Phase 6の提示時に明記する）

## Phase 5: 優先順位付け

各サブタスクを以下のTierに分類する。複数のTierの基準に該当する場合は、番号が小さいTierを優先する。

- **Tier1**: 「他者への依頼を予定している」または「他のタスクをブロックする（前提になっている）」タスク
  - 判定材料: Phase 2でユーザーが確認した内容（Phase 3-3で引き継ぎ判定済み）に加え、Agent自身が
    サブタスク一覧全体を見て構造的な依存関係（例:「BはAの成果物を前提にしている」）を分析し、
    ユーザーが申告していない依存も補完する
- **Tier2**: 不透明な部分があり時間を高い精度で見積もれない、または後続タスクの方針に影響しうる
  タスク（調査タスク等）
- **Tier3**: 実施すべきことが明確で、時間を高い精度で見積もれるタスク
  - 数値の工数見積もり自体は行わない（見積もり可能というTier分類に留める）

「進行順」は厳密な逐次ゲート（Tier1が全て完了しないとTier2に着手できない、等）ではなく、着手優先度
として扱う（依存関係がなければ他Tierのタスクと並行して進めてよい）。同一Tier内の並び順は、依存関係
が明確なものはその順を反映し、それ以外は順不同のフラットリストとする。

## Phase 6: 提示

以下を含む形でユーザーに提示する。

- サブタスク一覧（Tierごとにグルーピング。各タスクにタイトル・説明・該当する場合は依存/委譲の理由を付記）
- Phase 4の検証結果（全て合格したか、上限到達で打ち切った場合はその旨と未解決の指摘）

ユーザーがファイル保存を希望した場合は、Markdown形式で保存する（保存先パスはユーザーに確認する）。

## 検証者への指示

検証者は独立したサブエージェントとして起動し、元の要件・提案サブタスク一覧・以下の判定基準のみを
渡す（分割の意図や理由は渡さない）。

1. **Independent**: このサブタスクは他のサブタスクへの依存を最小限に抑え、単独で着手・完了できるか。
   避けがたい依存がある場合はそれを明記する
2. **Negotiable**: 実装の詳細まで固定されておらず、進め方に交渉・調整の余地が残っているか（仕様書の
   ように固定化されすぎていないか）
3. **Valuable**: このサブタスク単体が完了した際、要件の達成に対して意味のある価値をもたらすか
4. **Estimable**: 作業量をおおよそ見積もれるだけの情報が記述されているか
5. **Small**: 短期間で完了できる十分小さい単位になっているか
6. **Testable**: 完了したかどうかを明確な基準で判定できるか（完了の定義が曖昧でないか）
7. **網羅性**: サブタスク一覧全体で元の要件を過不足なくカバーしているか（不足している観点があれば
   具体的に指摘する。内容が重複するタスクがあれば指摘する）

各基準について不合格の場合は、該当するサブタスクと具体的な理由を報告する。

## エッジケース対応

- **要件がすでに十分小さく、分割の必要がない**: Phase 3で分割せず、その旨を明記してPhase 4の検証に
  そのまま進める
- **Phase 2でユーザーが実施事項を1件も挙げられない**: 要件を分割するには最低限の実施事項の認識が
  必要なため、要件自体の理解を一緒に深掘りしてから再度ヒアリングする
- **検証者が指摘した網羅性のギャップが、Phase 2でユーザーが触れていない領域に及ぶ**: Agentが自律的に
  不足分のタスクを追加してよい（Phase 4-3の通り）。ただし追加したタスクにはPhase 2のヒアリング情報が
  ないため、Tier1判定はAgentの依存関係分析のみに基づく
- **修正ループが上限（5回）に到達しても収束しない**: 打ち切り、現状のサブタスク一覧と未解決の指摘を
  そのままユーザーに提示する（Phase 4-3参照）。ユーザーの判断で追加の手動修正を促す
- **サブエージェント・別セッション等の独立実行手段が一切ない**: 実装文脈を含まない検証専用プロンプトを
  新たに組み立てて代替する（Phase 4-1参照）
- **ユーザーが要件ファイル/Issue URLを指定したが取得に失敗する**: 取得に失敗した旨を伝え、内容を
  チャットに貼り付けてもらう
- **深さ上限（3段階）に達してもSmallを満たさないタスクが残る**: 分割を止め、「これ以上機械的に
  分割していない」旨をそのタスクに明記して提示する（Phase 3-2参照）
