# Audit Requirements Based on IEEE 830 — 要件をIEEE 830の品質特性で監査する

渡された要件を、IEEE Std 830が定義するSRSの8つの品質特性の観点で評価し、改善点をフィードバックする
スキル。要件テキストの範囲内で判定できることと判定できないことを明確に切り分け、判定できない場合は
何を確認すればよいかを示す。問題が見つかった要件には統合した書き直し案を提示するが、それをどう扱うか
（採用する・別の直し方をする・保留する等）はユーザーの判断に委ねる。

## 全体の流れ

1. **要件の受け取り**（ユーザーとの対話）— 評価対象の要件を確認する
2. **要件の分割・粒度判定**（Agentが実施）— 単一要件か複数要件（要件セット）かを判定し、評価する特性を決める
3. **特性ごとの評価**（Agentが実施）— IEEE 830の8特性それぞれについて判定する
4. **改善案の作成**（Agentが実施）— 問題のある要件について統合した書き直し案を作る
5. **レポート生成と保存**（Agentが実施）— Markdownにまとめ、ローカルに保存する

## IEEE 830における8つの品質特性

このスキル内で以下の8項目として独立して用いる（定義はIEEE Std 830-1998のSRS品質特性の考え方に
基づく）。◎は単一要件でも評価可能、要は要件が2件以上必要（要件セット全体の性質）であることを示す。

1. **Correct（正確）**◎ — 要件が実際にシステムが満たすべき事柄を記述しているか
2. **Unambiguous（曖昧でない）**◎ — 一つの解釈しかできない記述になっているか
3. **Complete（完全）**要 — 想定される入力・状態のクラスに対する応答が要件セット内で規定されているか、
   未確定事項（TBD等）が残っていないか
4. **Consistent（一貫している）**要 — 要件間に論理的矛盾や用語の不整合がないか
5. **Ranked for importance and/or stability（重要度・安定度による優先順位付け）**要 —
   各要件に重要度または変更されにくさの情報が付与されているか
6. **Verifiable（検証可能）**◎ — 測定可能・テスト可能な基準で記述されているか
7. **Modifiable（変更可能）**◎/要 — 1要件が1つの関心事に限定されているか（単一要件でも判定可）、
   要件間の重複がないか（要件セットが必要）
8. **Traceable（追跡可能）**◎ — 一意なID・上位要求への参照など、追跡のための情報が付与されているか

## Phase 1: 要件の受け取り

- ユーザーから評価対象の要件を受け取る。チャット上の自由記述、またはファイルパス/Issue・チケットURLの
  指定を受け付ける
  - ファイルパス/URLが指定された場合、利用可能なツール（ファイル読み取り、Web取得、`gh`コマンド等）で
    内容の取得を試みる。取得できない場合はその旨を伝え、ユーザーに内容の貼り付けを依頼する
- 要件と呼べる記述が1件も読み取れない場合は、その旨を伝え対象の再指定を依頼する

## Phase 2: 要件の分割・粒度判定

- 入力を、独立して評価できる「要件」単位（番号付きリストの各項目、独立した"shall"/must文、箇条書きの
  各項目等）に分割する
- 分割方針が曖昧な場合（1文に複数の要求が混在している等）は、Agentが暫定的に分割し、その分割結果を
  Phase 5のレポート冒頭で明示する（ユーザーの意図と異なる場合に再指定できるようにするため）
- 分割後の要件数に応じて、Phase 3で評価する特性の範囲を決める
  - **1件のみ**: Correct/Unambiguous/Verifiable/Modifiable（1関心事の観点のみ）/Traceableを評価する。
    Complete/Consistent/Rankedおよび Modifiable の重複観点は「判定不可（要件が1件のみのため、2件以上の
    要件セットが必要）」とする
  - **2件以上**: 8特性すべてを評価する

## Phase 3: 特性ごとの評価

各要件（または要件セット全体で判定する特性についてはセット全体）について、以下の基準で判定する。
判定は **◯（満たす）/△（部分的に満たす・軽微な問題）/✗（満たさない）/対象外（要件数が足りない）/
判定不可（本文だけでは判断できない）** の5段階とし、単一のスコアには集約しない。判定不可の場合は、
判定するために何の情報が必要か（上位要求文書、ステークホルダーへの確認、優先度情報等）を明記する。

### 3-1. Correct（正確）

- 要件が実際のステークホルダーの必要と一致するかどうかは、要件本文だけからは判定できない。この観点は
  常に**判定不可**とし、必要な情報として「上位要求文書またはステークホルダーへの確認」を明記する
- 一方で、本文内で確認できる代理的な問題（自己矛盾する記述、要件セット内の他の記述と矛盾する事実、
  技術的に両立し得ない数値・制約の組み合わせ）は検出し、◯/△/✗で判定する。問題がなければ
  「本文内で確認できる範囲では問題なし。実際のニーズとの一致は別途確認が必要」と明記する

### 3-2. Unambiguous（曖昧でない）

- 複数の解釈が可能な語（主観的な形容詞・副詞「高速に」「適切に」「十分な」「ユーザーフレンドリーな」等、
  単位のない数値、「等」で終わる非網羅的な列挙）を検出する
- 定義なく使われている技術用語・独自用語があれば指摘する
- 解釈が割れる箇所は、実際に割れる2パターン以上の解釈例を挙げて具体的に示す

### 3-3. Complete（完全）

- 要件が2件以上の場合のみ評価する（1件のみの場合は対象外）
- 未確定事項（TBD/TODO/仮の値等）が残っていないかを確認する
- 要件文中で言及されている入力・状態のクラスに対して、想定される応答（正常系だけでなく異常系・境界値
  への応答）が要件セット内に規定されているかを確認する
- ある要件が暗に前提としている別の要件（例:「ログイン済みであること」を前提とする要件に対応する認証
  要件）が要件セット内に存在するかを確認する
- 要件セットそのものが上位のスコープ全体を余さず覆っているか（そもそも抜けている機能領域があるか）は
  本文だけでは判定できないため、この観点は**判定不可**とし、必要な情報として「上位スコープ文書・仕様書」
  を明記する

### 3-4. Consistent（一貫している）

- 要件が2件以上の場合のみ評価する（1件のみの場合は対象外）
- 同じ対象について異なる要件が矛盾する振る舞いを要求していないかを確認する
- 同じ概念に異なる用語が使われている、または異なる概念に同じ用語が使われていないかを確認する

### 3-5. Ranked for importance and/or stability（優先順位付け）

- 要件が2件以上の場合のみ評価する（1件のみの場合は対象外）
- 各要件に重要度または安定度（変更されにくさ）を示す情報（優先度ラベル、MoSCoW、Must/Should/Could等）
  が付与されているかを確認する
- 付与されていない場合は「優先順位・安定度の情報が付与されていない」と指摘するのみに留め、Agent自身が
  代わりに優先順位を提案することはしない（このスキルは評価とフィードバックのみを行う）

### 3-6. Verifiable（検証可能）

- 各要件が、測定可能・テスト可能な受け入れ基準（数値・条件・観測可能な振る舞い）で記述されているかを
  確認する
- 「〜であるべき」「使いやすいこと」等、テストでは判定できない主観的な表現を検出する

### 3-7. Modifiable（変更可能）

- 1つの要件文に複数の独立した関心事が混在していないか（1要件1関心事の原則）を確認する。これは単一
  要件でも判定できる
- 要件が2件以上の場合は、同じ制約・内容が複数箇所に重複して書かれていないかも確認する（1件のみの
  場合はこの観点のみ対象外とする）

### 3-8. Traceable（追跡可能）

- 各要件に一意なID・番号が付与されているか、上位要求への参照があるかを確認する
- 付与されていない場合は「追跡可能性の情報が付与されていない」と指摘し、必要な情報として「ID体系また
  は上位要求文書への参照」を明記する

## Phase 4: 改善案の作成

Phase 3で△または✗と判定された要件について、指摘された問題点をすべて反映した**1つの統合された
書き直し案**を作成する。判定不可だった観点（Correctの正確な一致確認、Complete/Ranked/Traceableの
外部情報が必要な部分等）は書き直しの対象にはせず、Phase 5で「判定に必要な追加情報」として別途扱う。

書き直し案には、どの修正がどの特性の指摘に対応しているかを説明文で明記する。書き直し案はあくまで
「案」であり、確定的な置き換えとして提示しない旨を明記する。

## Phase 5: レポート生成と保存

以下の構成でMarkdownレポートを生成する:

1. **概要**: 対象とした要件の総数、単一/要件セットのどちらとして扱ったか、Phase 2での分割結果
2. **要件×特性 判定表**: 行を各要件（Complete/Consistent/Rankedは「要件セット全体」の行として別途
   追加）、列をIEEE 830の8特性とし、セルに◯/△/✗/対象外/判定不可の記号を入れた表
3. **詳細**: 要件ごとに、△・✗・判定不可と判定した特性それぞれについて具体的な理由（本文中の該当箇所の
   引用を含む）を記載する
4. **改善案**: Phase 4で作成した統合済みの書き直し案を、対象要件・対応する指摘とともに提示する
5. **判定に必要な追加情報**: 判定不可だった項目と、それぞれ何があれば判定できるかの一覧

生成したMarkdownを`/tmp/audit-requirements-based-on-ieee830/<プロジェクト名>/<タイムスタンプ>/report.md`
にローカル保存する（プロジェクト名はリポジトリ/ディレクトリ名から推定、タイムスタンプは
`YYYYMMDD-HHMMSS`形式とし、同一プロジェクトへの再実行でも上書きしない）。保存先パスをユーザーに
報告する。

## エッジケース対応

- **要件が1件のみ**: Complete/Consistent/Rankedおよび Modifiable の重複観点を対象外とし、それらの
  評価には2件以上の要件セットが必要である旨をレポートに明記する
- **入力がユーザーストーリー形式等、"shall"文でない宣言的記述**: そのまま1件（または分割後の各項目）
  の要件として扱い、通常の特性評価を適用する
- **要件の分割方針が曖昧**（1文に複数の要求が混在している等）: Agentが暫定的に分割し、その分割結果を
  レポート冒頭に明示する（Phase 2参照）
- **ファイル/URL指定だが取得に失敗する**: その旨を伝え、内容をチャットに貼り付けてもらう
- **要件と呼べる記述が1件も読み取れない**: その旨を伝え、対象の再指定を依頼する（Phase 1参照）
- **判定不可だった項目についてユーザーが追加情報（上位要求文書、優先度、トレーサビリティ情報等）を
  提供した場合**: その情報をもとに該当項目のみ再評価し、判定を確定させる
- **`/tmp/audit-requirements-based-on-ieee830/...`の保存先に書き込めない**: その旨を伝え、代替の
  保存先をユーザーに確認する
