# Architecture Map — 構造マップ＋機能別データフロー図

対象コードベースを2段階で可視化するスキル。まず全体の依存関係をざっくり示す導入図で地図を見せ、
そこから気になる機能（エントリーポイント）を選ばせ、その機能の処理過程でクラス/構造体間を
やりとりされるデータの型と責務を示すデータフロー図に潜っていく。依存関係そのものより、
「どんなデータがどう流れるか」の理解を主目的とする。

## 全体の流れ

1. **入力の受け取り**（ユーザーとの対話）— 対象コードベースを確認する
2. **導入図の生成**（Agentが実施）— 依存関係・レイヤー構造の簡易マップを作る
3. **エントリーポイントの検出と選択**（ユーザーとの対話）— 機能の候補を提示し選んでもらう
4. **データフロー図の生成**（Agentが実施）— 選ばれた機能ごとに呼び出し連鎖とデータ型を追う
5. **出力**（Agentが実施）— 1つのインタラクティブHTMLにまとめ、ローカルにのみ保存する（**Artifactとしての発行は禁止**。情報の意図しない外部流出を防ぐため）

## Phase 1: 入力の受け取り

- 対象コードベースのパス（未指定ならカレントディレクトリのプロジェクトルート）を確認する
- モノレポ等で対象が自明でない場合のみ、対象範囲（リポジトリ全体か特定パッケージか）を確認する。
  自明な場合は確認を省略する

## Phase 2: 導入図（依存関係マップ）の生成

対象コードベース内で使われている言語を検出する。

- **優先言語（Java/Go/Node.js）が見つかった場合**: 標準ツールチェインで依存関係を機械的に抽出する
  - Java: `jdeps`（JDK同梱）でパッケージ/クラス間の依存を抽出
  - Go: `go list -deps` または `go mod graph` でパッケージ依存を抽出
  - Node.js: `import`/`require`文を静的にパースして依存を抽出
  - ツールが実行できない（未インストール・ビルド不可等）場合は、その言語の該当部分のみAI読解にフォールバックする
- **それ以外の言語**: ディレクトリ構造とコードをAIが読んで依存関係を解釈する
- ディレクトリ名・パッケージ名から層（例: `domain`/`usecase`/`infra`/`controller`/`UI`等）をヒューリスティックに推定し、AIの解釈で補正する
- 抽出した依存関係・層構造を、Mermaidの`flowchart`（層をサブグラフとして表現）で1枚のグラフにまとめる。
  ノードはモジュール/ディレクトリ単位とし、ファイル単位までは踏み込まない

この図は「地図」であり、次のPhase 3で選ぶ機能を探すための入り口として使う。

## Phase 3: エントリーポイントの検出と選択

コードベースを検索し、機能の起点となりうるエントリーポイントを検出する。判定基準は言語ごとに異なる。

- **Node.js**: ルーティング定義（`app.get/post/put/delete`、`router.xxx`等）、CLIコマンド定義（commander/yargs等）、`bin`フィールドが指す実行ファイル
- **Go**: `func main()`、HTTPハンドラ登録（`http.HandleFunc`、Gin/Echo等のルート定義）、RPCサービスのメソッド
- **Java**: Spring等の`@Controller`/`@RestController`に付与されたハンドラメソッド、JAX-RSの`@Path`メソッド、`public static void main`
- **その他の言語**: README・エントリーファイル（`main.py`、`cmd/`配下等）からAIが推定する

検出した候補（3〜10件程度に絞り、多すぎる場合は代表的なものや層の異なるものを優先）を、各候補が
何をする機能かの一言説明とともに提示し、`AskUserQuestion`等の構造化された選択手段で複数選択してもらう。
候補にない対象を自由記述で指定されても対応する。

## Phase 4: 機能ごとのデータフロー図の生成

選ばれたエントリーポイントごとに、以下を繰り返す。

- エントリーポイントを起点に、そこから呼び出されるクラス/構造体のメソッド呼び出しを、
  ソースコードを読んで辿る。全ファイルを読み切ろうとせず、対象クラス名・メソッド名をgrep等で
  検索しながら呼び出し先だけを追う
- **自コードベースの境界で打ち切る**: サードパーティライブラリ・DBドライバ・外部APIクライアントの
  内部実装までは追わない。境界を越える呼び出しは、越境する際にやりとりされるデータの型のみを
  ラベル付けした終端ノードとして表現する
- 呼び出し連鎖が深くなりすぎる場合（目安: 深さ7階層程度）は、それ以上を「…（さらに続く）」の
  省略ノードとして打ち切る
- 各呼び出しエッジには、渡される引数・返り値のデータについて**型名＋その型がどのような責務を
  持つデータなのか**（例: `OrderRequest — 注文APIのリクエストボディを保持するDTO`）を明記する
- ノード＝クラス/構造体、エッジ＝メソッド呼び出しとして、Mermaidの`flowchart`で機能ごとに1枚のグラフを作る。
  呼び出し順序（時系列）の厳密な表現は不要
- 複数の機能から呼ばれる共通クラスが登場しても、各機能の図はそれぞれ独立完結させる
  （同じクラスが別の図に重複して登場してもよい）

## Phase 5: 出力

**このマップは対象コードベースの構造・依存関係・データフローという機密性の高い情報を含みうるため、
Artifactとしての発行（外部への公開）は行わない。生成物は必ずローカルファイルとしてのみ保存する。**

1. HTMLを組み立てる前に、**`artifact-diagramming`スキルを読み込み**、Mermaid図の描画方法を確認する
   （`artifact-design`スキルは読み込まない。Artifact発行を前提としたデザイン指針であり、本スキルの
   出力はローカルファイルであって発行対象のArtifactではないため）
2. Phase 2の導入図と、Phase 4で生成した機能ごとのデータフロー図を、タブまたは一覧切り替えで
   行き来できる1つの自己完結HTMLにまとめる（Mermaid描画ライブラリをCDN等から読み込んでHTML内に
   組み込み、オフラインでも表示できるようにする。外部サービスへのアップロードは一切行わない）
3. 組み立てたHTMLを、対象コードベースの`.architecture-map/architecture-map.html`にローカル保存する
   （`Artifact`ツールは使用しない）
4. 対象コードベースの`.gitignore`に`.architecture-map/`が含まれていなければ追記する
   （生成物であり、コード変更のたびに古くなるため）
5. ローカル保存先のパスをユーザーに報告する。あわせて、このファイルは意図しない情報流出を防ぐため
   Artifactとして発行していないこと、共有したい場合はユーザー自身の判断で行う必要があることを伝える

## エッジケース対応

- **優先言語のツール（jdeps/go/node）が使えない**: 該当言語の部分のみAI読解にフォールバックし、
  その旨を完了報告に含める
- **エントリーポイントが1つも検出できない**: その旨を伝え、ユーザーに直接「どのファイル/関数を
  起点にするか」を指定してもらう
- **`.architecture-map/architecture-map.html`が既に存在する**: 上書きしてよいかユーザーに確認する
- **`.gitignore`が存在しない、または書き込めない**: その旨を完了報告に含め、手動での追記をユーザーに促す
- **呼び出し連鎖が外部境界だらけで、自コードベース内の情報がほとんど得られない**: 得られた範囲だけで
  図を作り、追跡が浅く終わった理由をユーザーに説明する
