# Boiled Me — 文書全体を意味を落とさず要約・凝縮する

入力された文書（形態は問わない）を分析し、論証構造を持つ箇所は論証図、持たない箇所は原文の順序を保った圧縮で
それぞれ要約対象を整理した上で、ユーザーがどの部分を削除・圧縮するかを対話的に決め、意味を落とさず読みやすい
短文の連なりに仕上げ、元の文章に反映するスキル。

## 全体の流れ

1. **入力の受け取りとソース判定**（Coding Agentが実施）— 対象文書を受け取り、取得元を判定する
2. **文書の分析（セグメント分割＋構造判定）**（Coding Agentが実施）— 文書をセグメントに分け、各セグメントを
   論証型／非論証型に分類し、それぞれに応じた構造（論証図 or 順序リスト）を作る
3. **構造の提示と削除・圧縮範囲の確認**（ユーザーとの対話）— 図とリストを提示し、削除・圧縮対象をユーザーと決める
4. **圧縮案文章の提示とレビュー**（ユーザーとの対話。承認まで3⇄4を反復可）
5. **元の文章への反映**（Coding Agentが実施）— ソース種別に応じた手段で反映する

## Phase 1: 入力の受け取りとソース判定

- 対象文書をユーザーから受け取る。未指定の場合は確認する
- 取得元を判定し、Phase 5の反映方法決定のために記録しておく:
  - **ファイル**: ローカルファイルパスが指定された場合。パスを記録する
  - **MCPリソース**: MCPツール経由（Google Drive/Docs、Gmail等）で取得した場合。使用したMCPサーバー名を記録し、
    対応する編集用toolの有無をこの時点で確認しておく
  - **テキスト**: チャットへの直接貼り付け、または上記いずれにも該当しない場合。反映先を持たない
- 判定が曖昧な場合は決め打ちせず、ユーザーに確認する

## Phase 2: 文書の分析（セグメント分割＋構造判定）

### 2-1. セグメント分割

- 文書を意味のまとまり（章・節・段落、または箇条書きの1項目など）単位でセグメントに分ける
- 分割の粒度は文書構造に従う。目安がなければ見出し／改段落／箇条書き項目を境界とする
- 1つのまとまりの中に性質の異なる内容（例: 手順の説明文とその理由づけ）が混在する場合は、文・節単位まで
  細分化してから個別に分類する（2-5節「ハイブリッドな項目」参照）

### 2-2. セグメントごとの分類

各セグメントを以下のいずれかに分類する:

- **論証型**: 主張（結論）とそれを支持する理由・根拠の関係がある。理由を間引いても結論自体は成立し続ける
  （＝支持の重複や省略に強弱をつけられる）箇所
- **非論証型**: 手順（時系列の一連の操作）、時系列の出来事の記述、箇条書きの事実の列挙、描写・物語など、
  支持関係を持たない箇所。各項目は基本的に独立した情報であり、順序や網羅性そのものに意味がある

判定に迷う場合の目安（両方に当てて考える）:
- 「この文を削除したら他の文の説得力が落ちるか？」→ Yesなら論証型
- 「この文の順番を入れ替えても意味が変わらないか？」→ 変わる（時系列・手順性がある）なら非論証型寄り

分類が一意に決まらないセグメントは無理に決め打ちせず、判定根拠を示した上でユーザーに確認する。

文書全体が非論証型のみ、または論証型のみで構成される場合もある。その場合は該当しない方の処理（論証図構築
または非論証リスト作成）を単純にスキップしてよく、ユーザーへの確認は不要。

### 2-3. 論証型セグメントの処理

論証図では以下の3要素を使う（[論証地図](https://ja.wikipedia.org/wiki/%E8%AB%96%E8%A8%BC%E5%9C%B0%E5%9B%B3)の概念に基づく）。
ユーザーへの提示時にも再利用する定義:

- **独立前提**（収束型）: 単独で結論を支持できる前提。複数あれば結論の裏付けが多重化される
- **従属前提**（連結型）: 複数の前提が組み合わさって初めて結論を支持する前提グループ。1つでも欠けると
  グループ全体の支持力が失われる
- **中間結論**（副結論）: 前提群に支持されつつ、さらに上位の結論を支持する結論。連鎖の途中に位置する

#### 分析手順

1. セグメント内の構造を分析し、そのセグメントの最終結論を特定する
    - 文書全体で最終結論が1つとは限らない。セグメントごとに最終結論が存在してよい
2. 最終結論を直接支持する要素を洗い出し、「独立前提」「従属前提グループ」「中間結論」のいずれかに分類する
3. 中間結論はさらにそれを支持する前提群に遡り、同様に再帰的に分類する
4. 各ノードを元の文章中の該当箇所（文・節単位）に対応づけておく（Phase 4の削除・再構成に必要）

#### ID付与

- 各ノードにIDを付与する（例: `C1`=最終結論、`IC1`=中間結論、`P2`=独立前提）
- 従属前提は、同じ結論/中間結論を共同で支持するグループ単位でグループIDも併せて付与する
  （例: `P1a`/`P1b` が `G1` に属する）

### 2-4. 非論証型セグメントの処理

1. セグメント内の項目（文・ステップ・列挙要素）を原文の順序どおりに洗い出す
2. 各項目にIDを付与する（`S1`, `S2`, ... 文書全体で一貫していれば採番方法は問わない）
3. 項目同士を比較し、**意味的に重複している項目**（同じ内容の言い換え、繰り返しの言及）を検出し、
   重複関係を記録する。これが非論証型における唯一の「安全な圧縮の手がかり」であり、論証図の独立前提のような
   重要度による取捨選択の根拠にはしない
4. 各項目の完全性（欠落すると手順が成立しない・実行できなくなる情報）に注意し、単なる言い回しの簡潔化と、
   情報の削除を明確に区別する
5. 重複かどうか判断に迷う項目は「重複の可能性あり」として記録し、決め打ちしない（Phase 3でユーザーに確認する）

### 2-5. ハイブリッドな項目

非論証型の項目（特に手順のステップ）に理由づけが付随している場合（例:「ログを削除する。容量を圧迫するため」）、
その理由部分だけを論証的な付属ノードとして扱ってよい:

```
1. [S3] ログを削除する
   └─→ [P] 理由: 容量を圧迫するため
```

この `P`（理由）はステップ `S3` に局所的に従属する注記であり、通常の論証図のように上位結論を持たない。
理由部分の省略可否は、ステップ本体を残したまま「理由の説明を省くかどうか」として扱い、ステップ自体の削除可否
とは別問題として確認する。

## Phase 3: 構造の提示と削除・圧縮範囲の確認

Phase 2-3で定義した論証図の3用語と、非論証型リストの考え方をユーザーに一度簡潔に説明してから提示する。
IDの先頭につく`C`, `IC`, `P`, `S`などについても意味を必ず述べること。

### 提示形式

文書全体をセグメント単位の見出し（`§1`, `§2`, ...）でまとめ、各セグメントに種別タグ（論証型／非論証型）を
付けて提示する。

**論証型セグメント**は、テキストのインデント＋ID付きアウトラインで提示する。**親ノードとの関係が独立前提か
従属前提かを、接続線の記号そのもので判別できるようにする**（ノードの後ろに文字で注記するだけでは、線を辿った時に
関係が分からないため、線種そのものを使い分ける）。

凡例:
- `─→`（単線矢印）: 独立前提・中間結論など、**その1本だけで親ノードを支持できる**関係
- `═⇒{Gn}`（二重線矢印＋グループID）: 従属前提。**同じグループIDを持つ線がすべて揃って初めて**親ノードを
  支持できる関係（1本でも欠けるとグループ全体の支持力が失われる）

**非論証型セグメント**は、矢印を使わない**番号付きフラットリスト**で、原文の順序のまま提示する。項目間に
支持関係は無く、**順序と網羅性を保つこと自体に意味がある**。重複が疑われる項目には注記を添える。

図と一緒にこれらの凡例をユーザーに添える。例:

```
[§1] 背景説明（論証型）
[C1] 最終結論の要約
├─→ [P2] 独立前提の要約                (単独矢印: これ1本だけでC1を支持できる)
└─→ [IC1] 中間結論1の要約              (単独矢印: IC1自体は独立してC1を支持する)
    ├═⇒{G1} [P1a] 従属前提aの要約      (二重矢印+同一グループID: P1aとP1bが揃って初めてIC1を支持)
    └═⇒{G1} [P1b] 従属前提bの要約

[§2] セットアップ手順（非論証型・時系列）
1. [S1] 依存パッケージをインストールする
2. [S2] 設定ファイルを作成する
   └─→ [P] 理由: デフォルト値では動作しないため
3. [S3] サービスを起動する
4. [S4] 起動後にログを確認する （※S2と内容が重複気味）
```

### 削除・圧縮対象の確認

削除・圧縮したい項目IDをユーザーに確認する。候補を提示しつつ自由記述も歓迎する形式にする
（構造化された選択肢提示手段があれば使う）。

**論証型セグメント**については、削除指定の構造的影響を検知し、実行前に警告・確認する:

- **従属前提グループの一部だけ削除**しようとした場合 → 「グループ全体で1つの支持根拠のため、一部だけ削除すると
  論証が崩れる」旨を伝え、グループ全体を削除するか維持するか確認する
- **中間結論を削除**しようとした場合 → それが支持している上位ノードへの影響（支持根拠が減る／結論への経路が
  途切れる）を説明し、上位ノードも合わせて削除するか、他の経路で結論の支持を保つか確認する
- **独立前提の削除** → 他に結論を支持する要素が残っていれば「安全な削除候補」である旨を伝える

**非論証型セグメント**については、論証構造による安全性の裏付けが無いため、以下の基準で確認する:

- **重複と判定済みの項目**の削除 → 「安全な削除候補（重複情報のため）」として伝える
- **重複と判定されていない項目**の削除 → 「この項目は独自の情報であり、削除すると手順・事実の一部が失われます。
  情報の欠落を伴う編集になりますが、削除しますか？」と確認する（構造的な安全性の根拠が無いため、判断は保守的
  な側に倒す）
- **手順の途中のステップ**を削除しようとした場合 → 後続ステップがそのステップの結果を前提としていないか
  可能な範囲で確認する（例: 設定ファイル作成ステップを消そうとしているが、後続に「作成した設定ファイルを
  編集する」ステップがある等）

確認が取れるまでこのフェーズを繰り返す。

## Phase 4: 圧縮案文章の提示とレビュー

確定した削除・圧縮対象に対応する原文箇所を取り除き、残った内容をつなぐ文章をセグメント種別に応じて生成する。

- セグメント間の元の並び順（§1, §2, ...）は維持する
- **論証型セグメント**:
  - 箇条書きでの構成を徹底する
  - 各文は端的にし、50文字程度に抑える
  - 前提→結論のつながりを示す場合、結論の文章を先頭に置きそれを支持する前提は一段深いインデントの箇条書きと
    する（文章間の論理構造を視覚的にわかりやすくするため）
- **非論証型セグメント**:
  - 原文の順序を厳密に保持する。結論ファーストの並べ替えは行わない
  - 各項目は50文字程度を目安に言い回しを簡潔化する
  - 重複と確認済みの項目のみを統合・削除する。それ以外の情報は落とさない

ユーザーに提示しレビューを依頼する。却下・修正依頼があればPhase 3の削除・圧縮範囲確認に戻る
（承認されるまで3⇄4を反復する）。承認が得られたらPhase 5へ進む。

## Phase 5: 元の文章への反映

Phase 1で判定したソース種別に応じて反映する:

- **ファイル** → Edit/Writeでそのファイルを直接編集する
- **MCPリソース** → 対応するMCPサーバーの編集用toolで反映する。編集用toolが見つからない、または権限がない場合は
  実行せず、代替手段（手動反映・テキスト出力への切り替え等）をユーザーに確認する
- **テキスト** → 反映先が無いため、最終文章をチャットに出力するのみ

反映後、変更箇所・反映先を簡潔に報告する。

## エッジケース対応

- **文章が長大で1つの論証図・非論証リストに収まらない**: 章・セクション単位で複数の論証図／リストに分割する
  方針をユーザーに確認してから進める
- **最終結論ノード（`C1`）自体の削除が指定された場合**: そのセグメントの要約が成立しなくなるため意図を確認する
- **削除指定が図・リストに存在しないID・自由記述の場合**: 元の文章から最も近いノード・項目・文言への
  マッピングを試み、一意に定まらなければユーザーに確認する
- **セグメントが論証型／非論証型のどちらか一意に決まらない場合**: 2-2節の判定根拠を示した上でユーザーに確認する
- **1つのまとまりに論証的要素と非論証的要素が混在する場合**: 2-5節のハイブリッド項目として扱うか、文単位で
  セグメントをさらに分割するかをユーザーに確認する
- **非論証型項目の重複判定に自信が持てない場合**: 重複と決め打ちせず「重複の可能性あり」として提示し、
  削除するかどうかはユーザーに確認する
- **MCPリソース由来だが対応する編集toolが無い/権限が無い場合**: 反映を実行せず代替手段を確認する
- **Phase 4の承認前**: 元の文章への破壊的操作（上書き）を行わない
