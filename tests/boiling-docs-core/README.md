# boiling-docs-core テスト

boiling-docs-core が要約・凝縮のあとも**情報を落としていないか**を検証する。入力文書に埋め込んだ「アンカー語」が出力に残っているかを機械的に照合する。コアは非対話なので、ユーザー承認を擬似化する指示は不要。

## 実行

```bash
tests/boiling-docs-core/run.sh                 # 全ケースを各3回実行
tests/boiling-docs-core/run.sh -n 5 01 06      # 実行回数を5回にし、01・06で始まるケースだけ実行
AGENT_CMD="<agent-cli>" tests/boiling-docs-core/run.sh
```

- `AGENT_CMD` は、**プロンプトを標準入力で受け取り、応答を標準出力に返す**コマンド（既定: `claude -p`）。Agent を差し替える箇所はここだけ
- プロンプトは `skills/boiling-docs-core/SKILL.md` の全文、対象文書、（あれば）追加制約から組み立てる。Agent のスキル呼び出し機能には依存しない
- 1ケースにつき N 回（`-n`）実行する。ケースは直列に実行するため、全ケースで 13 × N 回 Agent を呼ぶ
- いずれかのケースが FAIL なら終了コード 1

## 生成文章の確認

出力は `tests/boiling-docs-core/out/<timestamp>/` に保存する（`tests/*/out/` は `.gitignore` 済みで、Git の記録には残らない）。

| ファイル | 内容 |
|---|---|
| `summary.tsv` | 全ケースの判定と、種別ごとの通過数/総数 |
| `<case>/report.md` | **読む用**。アンカーごとの ○/×、入力文書、追加制約、期待値、生成文章（run ごと）を1ファイルに並べたもの |
| `<case>/run-N.md` | Agent の生の応答 |
| `<case>/run-N.draft.md` | 応答から抽出した要約案（`<draft>`。must / may / any / order の照合対象） |
| `<case>/run-N.plan.md` | 応答から抽出した圧縮方針の概要（`<plan>`） |
| `<case>/run-N.unresolved.md` | 応答から抽出した未確定事項（`<unresolved>`。flag の照合対象） |
| `<case>/run-N.check` | 照合結果（TSV） |
| `<case>/run-N.err` | Agent コマンドの標準エラー |

機械照合では、言い換えによる意味の脱落は検出できない。`report.md` の生成文章を目視で確認すること。

## 判定

| 種別 | 扱い |
|---|---|
| `must` / `order` / `any` / `flag` | 通過率が100%未満（N回のうち1回でも未通過）なら FAIL |
| `may` | 残存率の記録のみ。スキル改修前後の比較に使う |
| `format` | `<plan>`・`<draft>`・`<unresolved>` の3つをすべて応答から抽出できたか（記録のみ）。`<draft>` を抽出できない場合は応答全体で要約案の照合を行う |
| `idleak` | 出力に内部ID（`C1`、`IC1`、`P1a`、`G1`、`S1` など）が漏れていないか（記録のみ。正規表現による簡易判定のため誤検知がありうる） |

## ケースの書き方

`cases/<番号>-<名前>/` に、次のファイルを置く。

- `input.md`: 入力文書。1ケースに1つの罠だけを仕込み、残すべき事実には**言い換えにくい固有の語**（コマンド、数値、固有名詞）を含める
- `expect.txt`: 期待値。1行1項目、`#` で始まる行はコメント
- `constraints.txt`（任意）: 追加制約。1行1件、`「対象箇所の原文の引用」: 要望の自然文` の形。`#` で始まる行と空行は無視する。ファイルがなければ制約なしで呼び出す

```
must: --force                # 必ず残る。1回でも欠けたら FAIL
may:  ポート開放の理由         # 残らなくてもよい。残存率のみ記録
any:  案A | 案B | 案C         # 列挙のうち1つ以上が残る
order: step-a < step-b        # 最初の出現位置がこの順になる（`<` 区切りで連鎖可）
flag: 90%                     # <unresolved> に現れる。迷うべき箇所を迷えているかの確認
```

アンカーは `must` / `may` / `any` / `order` では `<draft>` に、`flag` では `<unresolved>` に対する**部分文字列の一致**で判定する（大文字小文字・空白は区別する）。

## ケース一覧

| # | 種別 | 仕込んだ罠 |
|---|---|---|
| 01 | 手順 | 順序依存。順序が崩れると成立しない |
| 02 | 手順 | 似ているが対象が違う2系統のステップ（重複として統合されてはならない） |
| 03 | 手順 | 実行に必須の数値・フラグが短い文に埋まっている |
| 04 | 列挙 | 独立した項目が多く、重複は1組だけ |
| 05 | 時系列 | 日時と出来事の順序に意味がある |
| 06 | 論証 | 従属前提グループ（片方だけ削ると支持が崩れる） |
| 07 | 論証 | 独立前提が複数あり、一部は削ってよい |
| 08 | 論証 | 中間結論を経由する連鎖（中間結論を削ると経路が切れる） |
| 09 | 混在 | 論証セグメントと手順セグメントが交互に並ぶ |
| 10 | ハイブリッド | 手順＋理由づけ（理由は省略可、ステップは省略不可） |
| 11 | 未確定事項 | 重複か判断できない近い2項目（統合せず残し、`<unresolved>` に載せる） |
| 12 | 追加制約 | 07の文書で、削られうる独立前提2つを制約で「残す」と指定（制約どおり残る） |
| 13 | 追加制約 | 08の文書で、最終結論の削除を求める制約（適用せず `<unresolved>` に載せる） |

11〜13 は、実在の Agent で通過率を測って期待値を調整する前の初期案である。

## 範囲外

対話skill `boiling-docs` のテストは、このテストの対象外。ソース種別（ファイル、MCP、テキスト）ごとの Phase 5 の分岐、未確定事項を1件ずつ質問する流れ、要望対応でコアを再呼び出しして Phase 3 に戻る経路、コアが見つからない場合の中断は検証しない。
