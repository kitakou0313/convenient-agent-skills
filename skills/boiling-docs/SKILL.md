# Boiling Docs — 文書全体を意味を落とさず要約・凝縮する（対話担当）

入力された文書（形態は問わない）を、ユーザーと対話しながら意味を落とさず読みやすい短文の連なりに要約・凝縮し、
元の文章に反映するスキル。**要約案の生成（文書の分析・圧縮方針の判定・要約案の作成）は `boiling-docs-core`
スキルが担当する。** このスキルは、コアの呼び出し、結果のユーザーへの提示、確認とレビューの取りまとめ、元の文章への
反映だけを担当する。

コアは非対話・ステートレスで、呼び出しのたびに元の文書から分析し直す。ユーザーの要望は、このスキルが「追加制約」に
変換してコアへ渡し直すことで反映する。

## 全体の流れ

1. **入力の受け取りとソース判定**（Coding Agentが実施）— 対象文書を受け取り、取得元を判定する
2. **コアの呼び出し**（Coding Agentが実施）— `boiling-docs-core` に文書と追加制約を渡し、結果を受け取る
3. **圧縮方針の提示と確認**（ユーザーとの対話）— 方針サマリの提示、未確定事項の質問、大枠のOK/NG確認
4. **要約案の提示とレビュー**（ユーザーとの対話。承認まで2⇄3⇄4を反復可）
5. **元の文章への反映**（Coding Agentが実施）— ソース種別に応じた手段で反映する

## Phase 1: 入力の受け取りとソース判定

- 対象文書をユーザーから受け取る。未指定の場合は確認する
- 取得元を判定し、Phase 5の反映方法決定のために記録しておく:
  - **ファイル**: ローカルファイルパスが指定された場合。パスを記録し、内容を読み込む
  - **MCPリソース**: MCPツール経由（Google Drive/Docs、Gmail等）で取得した場合。使用したMCPサーバー名を記録し、
    対応する編集用toolの有無をこの時点で確認しておく
  - **テキスト**: チャットへの直接貼り付け、または上記いずれにも該当しない場合。反映先を持たない
- 判定が曖昧な場合は決め打ちせず、ユーザーに確認する

## Phase 2: コアの呼び出し

`boiling-docs-core` スキルを使い、次の2つを渡す。

- **対象文書**: Phase 1で取得した本文テキスト
- **追加制約**: このスキルが会話中に溜めている制約のリスト（初回は空）。**毎回、これまでの全件を渡す**（コアは
  前回の呼び出しの状態を持たないため）。1件の形は次のとおり。引用が空の場合は文書全体への要望

```
「対象箇所の原文の引用」: 要望の自然文
```

スキルを名前で起動できない環境では、`boiling-docs-core/SKILL.md` を探して読み、その手順に従って処理する。
`boiling-docs-core` が見つからない場合は、処理を行わず、「`boiling-docs-core` が導入されていないため実行できない」
ことをユーザーに伝えて中断する。

コアの応答から `<plan>`・`<draft>`・`<unresolved>` の3ブロックを取り出して保持する。ブロックが揃っていない
場合は、1回だけコアを再呼び出しする。それでも揃わなければ、ユーザーに報告して中断する（元の文章は変更しない）。

## Phase 3: 圧縮方針の提示と確認

### 3-1. 方針サマリの提示

`<plan>` を、セグメント単位の一言サマリとしてユーザーに提示する。`<draft>` はこの時点では見せない。

```
[§1] 背景説明（論証型） → 理由づけ2点のうち重複気味の1点を削減予定
[§2] セットアップ手順（非論証型） → 2項目の内容が重複気味なので統合予定
[§3] まとめ（論証型） → 変更なし（すべての前提が結論を支持しており削減候補なし）
```

`<plan>` 中の「原文冒頭の引用」は、制約を作るために保持しておく。提示では、どのセグメントかが読み手に伝わる
範囲で引用を添えてよい。

### 3-2. 未確定事項の質問

`<unresolved>` が `なし` でなければ、**1件ずつ**ユーザーに質問する。1件ごとに「原文の引用／迷った点／コアが採用した
既定の判断」を添え、「既定のままでよい」だけの回答も許す。回答は、次のように制約に変換して溜める。

- 既定のままでよい → 制約を作らない
- 既定と違う判断を求められた → その箇所の引用と要望の自然文で制約を作る

全件の回答が出揃ってから、制約が1件でも増えていれば、**1回だけ**Phase 2に戻ってコアを再呼び出しし、新しい `<plan>`
を提示し直す。すべて既定のままなら再呼び出しは行わない。再呼び出しの結果に新たな未確定事項が現れた場合は、同様に
1件ずつ質問する（回答済みの箇所は再質問しない）。

### 3-3. 大枠の確認

方針サマリに対して、ユーザーへ大枠のOK/NGと自由記述の要望を確認する。削除IDの指定は不要で、「§1はもう少し
削ってよい」「§2はどちらも残したい」といった自然文の要望を歓迎する。

- 要望があれば、制約に変換して溜め、Phase 2に戻ってコアを再呼び出しし、`<plan>` を提示し直す
- ユーザーが `§N` で指した箇所は、提示中のサマリの引用に置き換えて制約の引用にする。引用が原文のどこを指すか
  一意に決まらない場合は、ユーザーに確認する
- 大枠のOKが取れたらPhase 4へ進む

## Phase 4: 要約案の提示とレビュー

直近のコア呼び出しで得た `<draft>` を、ユーザーに提示してレビューを依頼する。

- 承認が得られたらPhase 5へ進む
- 却下・修正依頼があれば、制約に変換して溜め、Phase 3に戻る（コアを再呼び出しし、`<plan>` を提示し直して
  大枠を確認する）。承認されるまで2⇄3⇄4を反復する

## Phase 5: 元の文章への反映

Phase 1で判定したソース種別に応じて反映する:

- **ファイル** → ファイル編集機能でそのファイルを直接編集する
- **MCPリソース** → 対応するMCPサーバーの編集用toolで反映する。編集用toolが見つからない、または権限がない場合は
  実行せず、代替手段（手動反映・テキスト出力への切り替え等）をユーザーに確認する
- **テキスト** → 反映先が無いため、最終文章をチャットに出力するのみ

反映後、変更箇所・反映先を簡潔に報告する。

## エッジケース対応

- **`boiling-docs-core` が見つからない**: 処理を行わず、導入が必要であることをユーザーに伝えて中断する
- **コアの応答が3ブロックの形式を満たさない**: 1回だけ再呼び出しし、それでも満たさなければユーザーに報告して中断する。
  元の文章は変更しない
- **文章が長大**: コアが章・セクション単位で個別に処理し、その旨を `<plan>` に明記する。このスキルが事前に
  分割する必要はない。分割の仕方に要望があれば、Phase 3の自由記述の要望として制約にする
- **文章の要旨（最終結論）に相当する内容の削除をユーザーが求めた場合**: コアはそのセグメントの要約が成立しなくなるため
  適用せず `<unresolved>` に載せる。載った場合は、Phase 3-2の手順で意図をユーザーに確認する
- **ユーザーの自由記述の要望が原文のどの箇所を指すか一意に定まらない場合**: 提示中のサマリから最も近い箇所への
  マッピングを試み、一意に定まらなければユーザーに確認する
- **MCPリソース由来だが対応する編集toolが無い/権限が無い場合**: 反映を実行せず代替手段を確認する
- **Phase 4の承認前**: 元の文章への破壊的操作（上書き）を行わない
