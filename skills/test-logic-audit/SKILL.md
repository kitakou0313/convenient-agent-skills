# Test Logic Audit — テストを論理学的アプローチで監査する

対象のテスト群を「前提」、テストが保証するコードの性質を「結論」とみなし、論証地図の考え方（独立前提・
従属前提・中間結論）でテストの論理構造を分析するスキル。単なるカバレッジ計測ではなく、テストから何が
妥当に演繹できるか／できないかを明らかにし、レビューや安全なリファクタリングの判断材料を提供する。

## 全体の流れ

1. **対象の特定**（ユーザーとの対話）— 監査対象を確認する
2. **仕様条件の収集**（Agentが実施）— 網羅性判定の物差しとなる条件を集める
3. **テストの実行・読解**（Agentが実施）— テストを実行またはAI読解し、各テストの内容を記録する
4. **論理構造の分析**（Agentが実施）— 網羅性判定＋論証構造の構築
5. **レポート生成と保存**（Agentが実施）— Markdownにまとめ、ローカルに保存する

## Phase 1: 対象の特定

- ユーザーから対象（実装ファイル・テストファイル・ディレクトリ等）の指定を受け取る
- 指定がない、または曖昧な場合:
  - まずAgentがリポジトリを探索する。`git diff`（変更差分）、変更されたテストファイル、
    それに対応する実装ファイルを手がかりに候補を洗い出す
  - 候補（対象実装ファイルとそれに対応するテストファイルのペア、3〜10件程度に絞る）を、
    それぞれ一言説明とともに提示し、ユーザーに選んでもらう
  - 候補が1つも見つからない場合は、その旨を伝えユーザーに直接指定してもらう

## Phase 2: 仕様条件の収集

Phase 4の網羅性判定で使う「対象が満たすべき条件（分岐・ケース）」のリストを作る。

- 外部仕様がある場合（README、docコメント、ユーザーが渡したIssue/仕様書、リポジトリ内の隣接ドキュメント等）は、
  そこから仕様条件を抽出する
- 実装コードを読み、分岐（if/switch/早期return/例外送出等）・型シグネチャ（Union型、Optional、
  エラー戻り値等）から条件を機械的に抽出する
- 両方が揃う場合は突き合わせ、外部仕様にはあるが実装に対応するロジックが見当たらない（またはその逆）
  といった齟齬も記録し、Phase 5のレポートに含める
- 各条件は同値分割・境界値の観点でも細分化する（例:「配列が空」「要素が1件」「要素が上限件数」等）

## Phase 3: テストの実行・読解

対象コードベースで使われている言語を検出する。

- **優先言語（Java/Go/Node.js）が見つかった場合**: 標準テストツールでテストを実行し、pass/fail結果と
  カバレッジ（行/分岐）を取得する
  - Java: `mvn test`/`gradle test`（JaCoCo等のカバレッジプラグインがあれば利用）
  - Go: `go test -cover ./...`
  - Node.js: `package.json`の`test`スクリプト（カバレッジオプションがあれば付与）
  - **実行前に、実行するコマンドをユーザーに提示し許可を得る**。読み取り専用の実行に限り、
    コードやデータを変更するコマンドは実行しない
  - ツールが実行できない（未インストール・許可が得られない等）場合は、その言語部分のみ
    静的読解にフォールバックする
- **それ以外の言語**: テストコードを実行せず、AIが静的に読解する

各テストについて以下を記録する:

- テスト名・対象（何の関数/メソッド/シナリオを検証しているか）
- アサーションの内容（何を、どんな条件で検証しているか）
- **アサーションの強さ**: 値そのものを検証しているか、型/存在のみの検証か、モック/スタブへの依存度、
  例外の中身まで見ているか等を評価し、「強い前提」「弱い前提（結論をあまり支持しない）」に分類する。
  値を検証しないトートロジー的なアサーション（常に真になる比較等）もここで検出する

## Phase 4: 論理構造の分析

テストレベル（unit/integration/e2e）は区別せず、「仕様条件に対する充足度」として統一的に扱う。
レベルの違いは対象とする条件の粒度の違い（unit=関数内の分岐、e2e=ユースケースのシナリオ分岐）として
吸収する。

### 4-1. 網羅性判定

Phase 2の仕様条件それぞれについて、Phase 3で読解したテストが対応しているかを判定し、条件×テストの
対応表（デシジョンテーブル）を作る。**単一のスコア/パーセンテージには集約しない**。実測できた
コードカバレッジ（行/分岐%）がある場合のみ、補助情報として数値のまま併記する。

未充足の条件については、想定される反例クラス（境界値・異常系・並行処理等、どのカテゴリの入力が
未検証か）を具体的に記録する。実際に失敗する入力を作って実証することはしない。

### 4-2. 論証構造の構築

論証地図の概念（[論証地図](https://ja.wikipedia.org/wiki/%E8%AB%96%E8%A8%BC%E5%9C%B0%E5%9B%B3)の
考え方をこのスキル内で独立して用いる）で、テスト（前提）からコードの性質（結論）への支持関係を
構築する:

- **独立前提**: 単独で結論を支持できるテスト（例: ある入力に対する出力を直接検証するテスト）
- **従属前提**: 複数のテストが組み合わさって初めて結論を支持するグループ（例: 正常系テストと
  異常系テストが揃って初めて「入力検証ロジックが正しい」と言える）
- **中間結論**: 個々のテストに支持されつつ、さらに上位の主張（例:「この関数は仕様を満たす」）を
  支持する結論

各結論について、支持する前提が実際にその結論を妥当に一般化できているか（前提が主張する範囲が
Phase 2の仕様条件の網羅範囲と一致するか）を判定する。Phase 3で「弱い前提」と分類したテストは
結論への支持力が弱いものとして扱い、単独では結論を支持できない、または限定的にしか支持しない旨を
明記する。

判定結果は「テスト群からは"結論X"が条件[a,b,c]の範囲で妥当に導ける」「条件dについては前提が
無い/弱いため導けない」という形で言語化する。

## Phase 5: レポート生成と保存

以下の構成でMarkdownレポートを生成する:

1. **テスト一覧**: 各テストが何を検証しているか（対象・アサーション内容・前提としての強さ）
2. **網羅性マップ**: 4-1のデシジョンテーブルをmermaidで可視化する（条件×テストの対応が視覚的に
   分かる形式。表とmermaid図を併用してよい）
3. **演繹的主張**: 4-2の論証構造をmermaidの`flowchart`で可視化し（独立前提/従属前提/中間結論/
   最終結論をノードとして表現）、「ここまでは言える／ここは言えない」を文章でも明記する
4. **不足テストケースの提案**: 網羅性マップで未充足だった条件について、テスト名（案）と検証すべき
   条件を提案する。テストコードそのものは生成しない

生成したMarkdownを`/tmp/test-logic-audit/<プロジェクト名>/<タイムスタンプ>/report.md`にローカル
保存する（プロジェクト名はリポジトリ/ディレクトリ名またはpackage.json/go.mod等から推定、
タイムスタンプは`YYYYMMDD-HHMMSS`形式とし、同一プロジェクトへの再実行でも上書きしない）。
保存先パスをユーザーに報告する。

## エッジケース対応

- **対象実装に対応するテストが1件も見つからない**: その旨を明示し、Phase 2で収集した仕様条件だけを
  もとに全条件を「未証明」としてレポートし、Phase 5の不足テスト提案に注力する
- **外部仕様・実装コードのどちらからも仕様条件を抽出できない**: ユーザーに仕様の所在
  （Issue、ドキュメント等）を確認する
- **テスト実行コマンドの検出に失敗する、または実行の許可が得られない**: 静的読解のみで進め、
  コードカバレッジ実測値が無いことをレポートに明記する
- **テストが失敗する（redな状態）**: 失敗しているテストは「成立していない前提」として扱い、
  そのテストが支持するはずだった結論は「未証明」に分類する
- **仕様条件と実装ロジックの間に齟齬がある**（外部仕様にはあるが実装が対応していない、またはその逆）:
  網羅性マップに齟齬として明記する
- **`/tmp/test-logic-audit/...`の保存先に書き込めない**: その旨を伝え、代替の保存先をユーザーに確認する
