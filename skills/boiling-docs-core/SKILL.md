# Boiling Docs Core — 文書を意味を落とさず凝縮する（非対話・純粋な変換）

文書を受け取り、意味を落とさず読みやすい短文の連なりに凝縮した**要約案**を返すスキル。ユーザーへの質問・確認では
一切停止せず、元の文章も書き換えない（入力としてファイルを読むのみ）。

- 論証構造を持つ箇所は、内部的に論証図を構築して支持関係が壊れない圧縮かどうかを検証する
- 持たない箇所は、重複排除を手がかりに原文の順序を保ったまま圧縮する
- 判断に迷う箇所は情報を残す側で処理し、迷った事実を `<unresolved>` に載せて呼び出し側に返す
- 呼び出しごとに元の文書から分析し直す（前回の呼び出しの状態を持たない）。やり直しや修正要望は、追加制約として
  渡し直してもらう

## 入力

- **対象文書**（必須）: 文書のテキスト、または読み取り専用のファイルパス。パスの場合は読み込むだけで、書き込まない
- **追加制約**（任意）: 呼び出し側（人間のレビュー結果など）が渡す要望のリスト。1件を次の形で受け取る。引用が空の
  場合は文書全体への要望として扱う

```
「対象箇所の原文の引用」: 要望の自然文
```

要望の例: 「この理由づけは残してほしい」「もう少し削ってよい」「重複と判定した項目だが別の意味なので両方残してほしい」

## 出力

次の3つのブロックを**この順に**返す。ブロックの外に説明文や前置きは書かない。内部ID（`C1`・`IC1`・`P1a`・
`G1`・`S1` など）はどのブロックにも出さない。

```
<plan>
[§1] 「原文冒頭の引用」 論証型 → 理由づけ2点のうち重複気味の1点を削減予定
[§2] 「原文冒頭の引用」 非論証型 → 2項目の内容が重複気味なので統合予定
[§3] 「原文冒頭の引用」 論証型 → 変更なし（すべての前提が結論を支持しており削減候補なし）
</plan>
<draft>
要約案の本文のみ
</draft>
<unresolved>
- 「原文の引用」 / 迷った点: 〜 / 既定の判断: 〜
</unresolved>
```

- `<plan>`: セグメント単位で1行ずつ。`§N` は文書内の並び順に振る表示用の番号。同じ行に付ける「原文冒頭の引用」は、
  そのセグメントの先頭にある原文をそのまま20文字程度写したもの（再呼び出し時にセグメントを特定する根拠になる）
- `<draft>`: 要約案の本文のみ（Phase 3の生成規則に従う）。方針の説明や注記は含めない
- `<unresolved>`: 迷った箇所を1件ずつ、原文の引用・迷った点・採用した既定の判断の3点で書く。1件もなければ `なし` とだけ書く

## 全体の流れ

1. **入力の読み取り** — 対象文書と追加制約を受け取る
2. **文書の分析（セグメント分割＋構造判定・内部検証）** — 論証型／非論証型に分類し、圧縮候補を内部的に検証する
3. **追加制約の適用と要約案の生成** — 制約を反映して圧縮候補を調整し、要約案を生成する
4. **出力** — `<plan>` `<draft>` `<unresolved>` を返す

## Phase 1: 入力の読み取り

- 文書テキストが渡されていればそれを使う。ファイルパスが渡されていれば読み込む（読み取りのみ）
- 対象文書が渡されていない場合は、質問せず、処理を行わずにその旨だけを返す
- 追加制約があれば、各制約の引用を原文中の該当箇所に対応づけておく（Phase 3で使う）

## Phase 2: 文書の分析（セグメント分割＋構造判定・内部検証）

### 2-1. セグメント分割

- 文書を意味のまとまり（章・節・段落、または箇条書きの1項目など）単位でセグメントに分ける
- 分割の粒度は文書構造に従う。目安がなければ見出し／改段落／箇条書き項目を境界とする
- 1つのまとまりの中に性質の異なる内容（例: 手順の説明文とその理由づけ）が混在する場合は、文・節単位まで
  細分化してから個別に分類する（2-5節「ハイブリッドな項目」参照）
- 文書が長大で1つの論証図・非論証リストに収まらない場合は、章・セクション単位に分けて個別に処理する。
  ユーザーには確認せず、章単位で個別に処理したことを `<plan>` の該当行の方針に明記する

### 2-2. セグメントごとの分類

各セグメントを以下のいずれかに分類する:

- **論証型**: 主張（結論）とそれを支持する理由・根拠の関係がある。理由を間引いても結論自体は成立し続ける
  （＝支持の重複や省略に強弱をつけられる）箇所
- **非論証型**: 手順（時系列の一連の操作）、時系列の出来事の記述、箇条書きの事実の列挙、描写・物語など、
  支持関係を持たない箇所。各項目は基本的に独立した情報であり、順序や網羅性そのものに意味がある

判定に迷う場合の目安（両方に当てて考える）:
- 「この文を削除したら他の文の説得力が落ちるか？」→ Yesなら論証型
- 「この文の順番を入れ替えても意味が変わらないか？」→ 変わる（時系列・手順性がある）なら非論証型寄り

分類が一意に決まらないセグメントは、**非論証型として処理する**（重複と確認できた項目以外は落とさない、情報を
残す側の扱い）。判定根拠を `<unresolved>` に載せる。

文書全体が非論証型のみ、または論証型のみで構成される場合もある。その場合は該当しない方の処理（論証図構築
または非論証リスト作成）を単純にスキップしてよい。

### 2-3. 論証型セグメントの内部検証処理

この節の分析結果（論証図・ID）は出力に含めず、圧縮候補の判定と検証にのみ内部的に使う。

論証図では以下の3要素を使う（[論証地図](https://ja.wikipedia.org/wiki/%E8%AB%96%E8%A8%BC%E5%9C%B0%E5%9B%B3)の概念に基づく）:

- **独立前提**（収束型）: 単独で結論を支持できる前提。複数あれば結論の裏付けが多重化される
- **従属前提**（連結型）: 複数の前提が組み合わさって初めて結論を支持する前提グループ。1つでも欠けると
  グループ全体の支持力が失われる
- **中間結論**（副結論）: 前提群に支持されつつ、さらに上位の結論を支持する結論。連鎖の途中に位置する

#### 分析手順

1. セグメント内の構造を分析し、そのセグメントの最終結論を特定する
    - 文書全体で最終結論が1つとは限らない。セグメントごとに最終結論が存在してよい
2. 最終結論を直接支持する要素を洗い出し、「独立前提」「従属前提グループ」「中間結論」のいずれかに分類する
3. 中間結論はさらにそれを支持する前提群に遡り、同様に再帰的に分類する
4. 各ノードを元の文章中の該当箇所（文・節単位）に対応づけておく（Phase 3の削除・再構成に必要）

各ノードに内部管理用のIDを付与する（例: `C1`=最終結論、`IC1`=中間結論、`P2`=独立前提）。従属前提は同じ結論/
中間結論を共同で支持するグループ単位でグループIDも併せて付与する（例: `P1a`/`P1b` が `G1` に属する）。
これらのIDは出力に出さない。

#### 圧縮候補の判定

分析結果をもとに、以下の基準で「支持構造を壊さない安全な圧縮候補」を内部的に選定する:

- **独立前提**: 他に結論を支持する要素が残っていれば圧縮候補にできる
- **従属前提グループ**: グループの一部だけを圧縮候補にしない（1つでも欠けるとグループ全体の支持力が
  失われるため）。候補にする場合はグループ全体をまとめて対象にする
- **中間結論**: 削減候補にする場合、それが支持している上位ノードへの影響（支持根拠が減る／結論への経路が
  途切れる）を評価し、他の経路で結論の支持が保てないなら候補から外す

#### 検証

圧縮候補を適用したと仮定して論証図をたどり直し、最終結論の支持が破綻していないかを確認する。破綻する
場合は候補を再検討する。この判定・検証結果が `<plan>` の一言サマリの根拠になる。

### 2-4. 非論証型セグメントの処理

1. セグメント内の項目（文・ステップ・列挙要素）を原文の順序どおりに洗い出す
2. 各項目に内部管理用のIDを付与する（`S1`, `S2`, ... 文書全体で一貫していれば採番方法は問わない）。IDは
   出力に出さない
3. 項目同士を比較し、**意味的に重複している項目**（同じ内容の言い換え、繰り返しの言及）を検出し、
   重複関係を記録する。これが非論証型における唯一の「安全な圧縮の手がかり」であり、論証図の独立前提のような
   重要度による取捨選択の根拠にはしない
4. 各項目の完全性（欠落すると手順が成立しない・実行できなくなる情報）に注意し、単なる言い回しの簡潔化と、
   情報の削除を明確に区別する
5. 重複かどうか判断に迷う項目は「重複の可能性あり」として扱い、**統合せず両方残す**。迷った事実を
   `<unresolved>` に載せる

### 2-5. ハイブリッドな項目

非論証型の項目（特に手順のステップ）に理由づけが付随している場合（例:「ログを削除する。容量を圧迫するため」）、
その理由部分だけを論証的な付属ノードとして内部的に扱ってよい:

```
1. [S3] ログを削除する
   └─→ [P] 理由: 容量を圧迫するため
```

この `P`（理由）はステップ `S3` に局所的に従属する注記であり、通常の論証図のように上位結論を持たない。
理由部分の省略可否は、ステップ本体を残したまま「理由の説明を省くかどうか」として扱い、ステップ自体の削除可否
とは別問題として内部的に判定する（この構造は出力せず、`<plan>` の一言サマリに反映する）。

理由づけを省くかどうか判断に迷う場合は、**省かずに残す**。迷った事実を `<unresolved>` に載せる。

## Phase 3: 追加制約の適用と要約案の生成

### 3-1. 追加制約の適用

追加制約が渡されている場合、Phase 2の内部判定に反映してから要約案を生成する。各制約の引用が指す原文の箇所を
特定し、次のように扱う:

- 論証型セグメントについて「特定の理由づけを残してほしい」: その要素を圧縮候補から除外した上で、論証図で
  支持構造が壊れないか内部的に再検証する
- 論証型セグメントについて「もう少し削ってよい」: 支持構造を壊さない範囲で圧縮候補を増やす
- 非論証型セグメントについて「重複と判定した項目だが実は別の意味」: 重複判定を取り消し、圧縮候補から除外する
- 文書全体への要望（引用が空）: 全セグメントの判定に反映する

次の制約は**適用せず**、情報を残す側で処理して `<unresolved>` に載せる:

- 引用が原文のどこを指すか一意に定まらない（最も近い箇所へのマッピングを試みても決まらない）
- 文書の要旨（最終結論）に相当する内容の削除を求めている（そのセグメントの要約が成立しなくなる）
- 他の制約と矛盾している

### 3-2. 要約案の生成

圧縮方針に基づき、対応する原文箇所を取り除き、残った内容をつなぐ文章をセグメント種別に応じて生成する。

- セグメント間の元の並び順（§1, §2, ...）は維持する
- **論証型セグメント**:
  - 箇条書きでの構成を徹底する
  - 各文は端的にし、50文字程度に抑える
  - 前提→結論のつながりを示す場合、結論の文章を先頭に置きそれを支持する前提は一段深いインデントの箇条書きと
    する（文章間の論理構造を視覚的にわかりやすくするため）
- **非論証型セグメント**:
  - 原文の順序を厳密に保持する。結論ファーストの並べ替えは行わない
  - 各項目は50文字程度を目安に言い回しを簡潔化する
  - 重複と確認済みの項目のみを統合・削除する。それ以外の情報は落とさない

## エッジケース対応

- **対象文書が渡されていない**: 質問せず、処理を行わずにその旨だけを返す
- **文章が長大で1つの論証図・非論証リストに収まらない**: 確認せず、章・セクション単位で個別に処理し、`<plan>` に明記する
- **文章の要旨（最終結論）に相当する内容の削除を求める制約**: 適用せず、`<unresolved>` に載せる
- **制約の引用が原文のどの箇所を指すか一意に定まらない**: 最も近い箇所へのマッピングを試み、定まらなければ適用せず
  `<unresolved>` に載せる
- **セグメントが論証型／非論証型のどちらか一意に決まらない**: 非論証型として処理し、判定根拠を `<unresolved>` に載せる
- **1つのまとまりに論証的要素と非論証的要素が混在する**: 2-5節のハイブリッド項目として扱うか、文単位でセグメントを
  さらに分割し、どちらにしたかを `<unresolved>` に載せる
- **非論証型項目の重複判定に自信が持てない**: 統合せず両方残し、`<unresolved>` に載せる
- **ユーザーへの質問・確認・元の文章への書き込み**: 行わない。確認が必要な事柄はすべて `<unresolved>` で呼び出し側に返す
