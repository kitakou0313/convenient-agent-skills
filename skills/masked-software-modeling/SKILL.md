# Masked Software Modeling — ソフトウェアロジックの穴埋め学習

既存のソフトウェアプロジェクトの一部のロジックを削除（マスク）し、ユーザー自身にそのロジックを再実装させることで、
対象ソフトウェアへの理解を深めるスキル。Masked Language Modeling（MLM）の考え方をソフトウェアに応用したもの。

## 全体の流れ

1. **問題生成**（Coding Agentが実施）— ソフトウェアを調査し、ロジックを削除して問題を作る
2. **実装**（ユーザーが実施）— マスクされた部分をユーザー自身が実装する。Agentはヒントのみ提供する
3. **解説**（Coding Agentが実施。別セッションでもよい）— ユーザーの求めに応じて元のコードと解説を提示する

このスキルは1回の依頼で完結せず、上記3フェーズに渡って複数回・複数セッションで呼び出される。
呼び出しごとに、次の「モード判定」に従ってどのフェーズを実施すべきか判断すること。

## ユーザーとのコミュニケーション時に注意すること
- **ユーザーにコードについて話す際、対象のソフトウェア固有の用語、定義については文中で言及する前に必ず定義、解説、具体例を述べること**
  - ユーザーは対象のソフトウェアに対しての知見がないことが想定されるため、コード内の単語をそのまま解説しても理解できません。

## モード判定

以下の優先順位でどのフェーズを実施すべきか判断する。

1. **明示的な意図**: ユーザーの発言から明らかな場合はそれに従う
   - 新しいソフトウェア名/URLの指定、「問題を作って」「マスクして」等 → Stage 1（問題生成）
   - 「ヒントちょうだい」「詰まった」等 → Stage 2（ヒント提供）
   - 「答え見せて」「解説して」「正解は？」等 → Stage 3（解説）
2. **状態からの推定**（意図が曖昧、または引数なしの再訪の場合）:
   - カレントディレクトリ（または `masked-modeling-workspace/` 配下）が `masked-modeling/*` ブランチにおり、
     `.masked-modeling/problem.json` が存在するか確認する
   - 存在する場合、`problem.json` の `test_command`（対象ソフトウェア自身が用意しているテストコマンド）を実行する
     - 失敗する → まだ実装途中（Stage 2）。ヒントが欲しいか、答えを見たいか（Stage 3への移行）をユーザーに確認する
     - 成功する → 実装が完了している可能性が高い。解説（Stage 3）に進んでよいか確認する
   - 存在しない場合 → 新規の問題生成（Stage 1）とみなし、対象ソフトウェアをユーザーに確認する
3. **複数の問題が存在する場合**: `git branch --list 'masked-modeling/*'` で列挙し、各ブランチの
   `.masked-modeling/problem.json` から対象ロジックの説明を読み取ってユーザーに選ばせる
   （`git show <branch>:.masked-modeling/problem.json` で作業ツリーを汚さずに内容を確認できる）。
   常にユーザーに選ばせ、Agentが勝手に1つに決めつけない。

## Stage 1: 問題生成（Coding Agentが実施）

### 1-1. 対象ソフトウェアの調査

- 対象のソフトウェア（リポジトリURLまたはローカルパス、必要なら対象コミット/タグ/ブランチ）をユーザーに確認する
- `./masked-modeling-workspace/<repo名>/` に`git`コマンドでcloneする
  - 同名ディレクトリが既に存在する場合は再cloneせず、既存のものを再利用してよいかユーザーに確認する
- README・CONTRIBUTING・package.json/pyproject.toml/go.mod/Cargo.toml等のマニフェスト・CI設定
  （`.github/workflows`等）からビルド方法とテストコマンドを特定する
- **検証手段は必ず対象ソフトウェア自身が用意しているテスト方法（`npm test`/`go test`/`pytest`/`make test`等、
  README・CI設定に明記されたコマンド）を使用する。Agent側で独自にテストコードを新規作成しない。**
  これは、削除箇所の実装が完了したかどうかをユーザー自身がそのソフトウェア本来の品質基準で検証できるようにするため
- 特定したテストコマンドを実際に実行し、**マスク前の状態でテストが通ることを確認する**
  - 通らない場合はここで止まる（問題生成を進めない）。環境構築の不足かソフトウェア側の既知の問題かをユーザーに報告し、
    対応方針（依存関係の追加インストール、対象コミットの変更、失敗テストの除外等）を確認する
- 確認できたテストコマンド・対象コミットハッシュ・ベースブランチ名を記録しておく（後で`problem.json`に書く）

### 1-2. 出題内容のヒアリング

まず、コードベース全体を**網羅的に調査**する。

その後、このソフトウェアについて以下を説明する。
- このソフトウェアが解決している問題
  - 背景、どのような問題を解決しているソフトウェアなのか
- ユーザーがソフトウェアを実行するときの流れ

その後、問題の候補となりそうなロジック（主要モジュール・関数・アルゴリズム等）を2〜5件程度リストアップしてユーザーに提示する。構造化された選択肢提示手段があれば利用する。提示するときはそのロジックがソフトウェア全体の処理の中でどのような役割を行なっているのかをも提示する。提示は「候補を挙げたうえで自由記述も歓迎する」形にし、候補にない対象を指定されても対応する。

以下の2点を聞き取る。ユーザーの依頼から自明な点は確認のみに留める。

1. **対象ロジック**: 提示した候補、またはユーザー指定の対象
2. **問題の粒度**: 数行の処理の穴埋め 〜 複数関数・複数ファイルにまたがる処理全体、のどのレベルか
   - 粒度が大きい（複数ファイルにまたがる）場合は、対象ファイル一覧を明示してユーザーに最終確認を取ってから
     次に進む（マスク範囲の暴走を防ぐため）

### 1-3. 問題用ブランチの作成

対象ロジックが確定してから、対象ロジックを表す短いケバブケースの `<slug>` を決め、ベースブランチのHEAD
（または指定コミット）から `masked-modeling/<slug>` ブランチを作成する。
（ヒアリング前にブランチを切ると、対象未確定のままブランチ名が決まってしまうため、ブランチ作成はヒアリング後に行う）
既に同名スラッグのブランチが存在する場合は連番などで衝突を避ける。

### 1-4. マスキング（コード削除）の実施

1. `.masked-modeling/problem.json`（スキーマは後述）を作成する。この時点ではコードには編集を加えない。
2. 対象ロジックの実装本体を削除し、関数シグネチャ・型・周辺構造は残したまま、
   明確なプレースホルダ（例: `raise NotImplementedError("masked-software-modeling: <対象の一言説明>")`
   やコメント `# TODO(masked-software-modeling): ここを実装する`）に置き換える
   - プレースホルダのコメントには**ヒントになる実装方針を書かない**。対象の一言説明のみ

### 1-5. 検証（赤になることの確認）

- `problem.json` の `test_command`（対象ソフトウェア自身のテストコマンド）を実行し、
  **関連するテストが失敗/エラーになること**を確認する
  - 通ってしまった場合はマスクが不十分。1-4に戻り、より本質的な範囲までマスクを広げる
  - 無関係な原因（環境起因のflaky等）で失敗している場合は原因を切り分け、対象ロジックの欠如による失敗であることを
    確認してから次に進む
- 確認できた失敗テスト名・概要を `problem.json` の `baseline_red_summary` に記録する（コードの答えは含めない）

### 1-6. 問題の提示

ユーザーに以下を提示する。

- マスクした対象（ファイル・関数・大まかな役割）と、なぜこのロジックが重要かの簡単な位置づけ
- 問題の粒度・タスクの一言説明（コード自体は再掲しない）
- ローカルでの検証方法（`test_command` の実行方法。対象ソフトウェア自身のテスト方法であることを明記）
- 「ここから先はユーザー自身が実装するフェーズであり、Agentはヒントのみ提供すること」の明示

## 問題メタデータ（`.masked-modeling/problem.json`）

問題ブランチのルートに配置する。

```json
{
  "slug": "lru-cache-eviction",
  "repo_url": "https://github.com/xxx/yyy",
  "base_commit": "abcdef...",
  "target_description": "LRUキャッシュの追い出し（eviction）ロジック",
  "granularity": "single-function",
  "masked_paths": ["src/cache/lru.go"],
  "test_command": "go test ./...",
  "baseline_green_confirmed_at": "2026-07-27T10:00:00+09:00",
  "baseline_red_summary": "TestLRUEviction, TestLRUCapacity が失敗",
  "hints_given": [
    { "level": 1, "text": "...", "given_at": "..." }
  ],
  "candidates_considered": [
    { "description": "LRUのeviction処理", "chosen": true },
    { "description": "設定ファイルのパース処理", "chosen": false }
  ]
}
```

**答え（削除前のコード本文）はこのファイルに書かない。** 
`base_commit`の値には元コードがそのまま残っている。答えは`git show <base_commit>:<path>`（元のファイル全体）で取得する。git-nativeな取得に統一することで、答えの二重管理・drift・メタデータファイルからの答えの漏洩を避ける。

## Stage 2: 実装（ユーザーが実施）

このフェーズの主体はユーザー。Agentは求められない限り介入しない。ユーザーは:

- マスクされた部分を自分で実装する
- `test_command`（対象ソフトウェア自身のテストコマンド）を実行し、通るまで試行錯誤する
- 詰まったらAgentにヒントを求める

### ヒント提供の指針（ユーザーから求められた場合のみ）

**元のコード・削除前後の完全なdiffは絶対に提示しない。** 以下の3段階のレベルを、要求の強さに応じて段階的に開示する。

1. **レベル1（着眼点）**: 関連する既存コード・パターンが他の箇所にないか、どこに注目すべきかの問いかけ
2. **レベル2（方針）**: 使うべきアルゴリズム名・データ構造・処理の骨組みを、具体的なコードなしで説明する
3. **レベル3（かなり具体的な誘導）**: ユーザーが明示的に「まだわからない」と重ねて求めた場合のみ。
   擬似コードや部分的なスケルトンまでは示してよいが、削除された行そのものは書かない

ユーザーが「もう答えを見せて」と明示的に求めた場合はヒントではなくStage 3への移行として扱い、
演習を終了してよいか確認してから解説フェーズに進む。

提供したヒントはレベルと内容を `.masked-modeling/problem.json` の `hints_given` に追記する
（同じレベルの重複提供を避け、次のヒントで段階を上げる判断材料にするため。別セッションでも参照できる）。

ユーザーに求められればテストを代わりに実行して合否・失敗テスト名を報告してよいが、理由の説明はヒントの範囲内に留める。

## Stage 3: 解説（Coding Agentが実施。別セッションでもよい）

### 3-1. 対象問題の特定

- カレントブランチが `masked-modeling/*` に一致し `.masked-modeling/problem.json` があればそれを対象とする
- 複数の問題が存在し曖昧な場合は「モード判定」の手順3に従いユーザーに選ばせる

### 3-2. 回答の取得（git-native）

- `problem.json` の `base_commit` を読み、`git show <base_commit>:<path>`（`masked_paths` それぞれ）で
  マスク前の元コードを取得する。

### 3-3. 解説の提示

- 元のコード（答え）を提示する
- なぜそのロジックがそう実装されているか、周辺アーキテクチャとの関係、設計上のポイントを解説する
- `hints_given` を踏まえ、「ここまでのヒントで触れた点」との対応関係を補足する
- ユーザーの作業ツリーに実装途中のコードが残っていれば、答えとの差分を示し、良かった点・改善点を伝える
- 解説後、別の問題を続けて生成するか確認する

## エッジケース対応

- **テストコマンドが不明/特殊なビルドシステム**: README・CI設定から推定できない場合はユーザーに直接確認する。
  **Agent側で独自の検証コードを新規作成して代替しない**（対象ソフトウェア自身のテスト方法を使うという原則を保つため）
- **マスク前からテストが赤い（既存の失敗）**: 問題生成の信頼できる基準にならないため先に進めず、
  対象コミット/バージョンの変更や失敗テストの除外方針をユーザーと決める
- **同一リポジトリに複数の問題が存在**: 常にブランチ名＋`problem.json`の対象説明でユーザーに選ばせる。
  勝手に1つに決めつけない
- **問題のやり直し/再生成の依頼**: 既存ブランチを上書きせず、新しいslugで別ブランチを作成する
  （過去の試行を保持するため）。既存ブランチの削除は明示的な確認を取った場合のみ行う
- **粒度が大きく複数ファイルにまたがる**: マスク実行前に対象ファイル一覧を明示し、ユーザーの最終確認を取る
- **ユーザーが実装途中のコードを見せて「これが答え？」と聞いてきた**: 元コードの提示はせず、
  テスト実行結果での合否確認に留める（安易な答え合わせでの種明かしを避ける）
- **作業ツリーに未コミットの変更がある状態でのモード判定/git操作**: 破壊的なgit操作
  （checkout, reset等）はユーザーの実装中の変更を消しうるため、明示的な確認なしに行わない
