# Boiling Docs Core — 文書を読みやすく書き直す（非対話・純粋な変換）

文書を受け取り、内容を変えずに読みやすく書き直した**改善案**を返すスキル。ユーザーへの質問・確認では一切停止せず、
元の文章も書き換えない（入力としてファイルを読むのみ）。

- 原文の内容は**削除しない**。許す操作は、並べ替え・文の分割・表記の統一・構造化・定義と具体例の追加だけである
- 読みやすさを次の2視点で整える
    - 意味論の読みやすさ: 主張の並び順・結論の位置・用語の定義
    - 記号的な読みやすさ: 表記・文の長さと構造・箇条書き
- 判断に迷う箇所は、原文を変えない側で処理し、迷った事実を `<unresolved>` に載せて呼び出し側に返す
- 呼び出しごとに元の文書から分析し直す（前回の呼び出しの状態を持たない）。やり直しや修正要望は、追加制約として
  渡し直してもらう
- 対象は日本語の文書を想定する。文字数の基準は日本語のものである

## 入力

- **対象文書**（必須）: 文書のテキスト、または読み取り専用のファイルパス。パスの場合は読み込むだけで、書き込まない
- **想定読者**（任意）: 文書を読む人の自然文の記述。例は「新卒のバックエンドエンジニア」。未指定の場合は、文書の分野・文体・
  既出の語から推定する。推定した読者像は `<plan>` の `[全体]` 行に書き、推定の根拠を `<unresolved>` に載せる
- **追加制約**（任意）: 呼び出し側（人間のレビュー結果など）が渡す要望のリスト。1件を次の形で受け取る。引用が空の
  場合は文書全体への要望として扱う

```
「対象箇所の原文の引用」: 要望の自然文
```

要望の例:

- 「この語の定義は〜としてほしい」
- 「この語の表記は〇〇に統一してほしい」
- 「この箇所は並べ替えないでほしい」
- 「この文は分割しないでほしい」

## 出力

次の3つのブロックを**この順に**返す。ブロックの外に説明文や前置きは書かない。

```
<plan>
[全体] 想定読者: 新卒のバックエンドエンジニア（推定）／ 結論: §3 を先頭へ移動／ 表記統一: 「利用者」→「ユーザー」
[§1] 「原文冒頭の引用」 論証型 → 複文2文を分割。「冪等性」の定義を補った（一般知識で補足）
[§2] 「原文冒頭の引用」 非論証型 → 手順を番号付き箇条書きに整理。「PITR」の定義を移動（原文から）
[§3] 「原文冒頭の引用」 論証型 → 結論の文を先頭へ移動。ほかは変更なし
</plan>
<draft>
改善案の本文のみ
</draft>
<unresolved>
- 「原文の引用」 / 迷った点: 〜 / 既定の判断: 〜
</unresolved>
```

- `<plan>`: 先頭に `[全体]` 行を1行、続けてセグメント単位で1行ずつ書く
    - `[全体]` 行には、想定読者（推定した場合は「（推定）」を付ける）・結論の移動元・表記統一の対応を書く。該当がない項目は
      `なし` と書く
    - `§N` は文書内の並び順に振る表示用の番号である。原文の並び順で振り、並べ替えた場合は、その行の方針に移動先を書く
    - 「原文冒頭の引用」は、そのセグメントの先頭にある原文をそのまま20文字程度写したものである。再呼び出し時に
      セグメントを特定する根拠になる
    - 定義と具体例を置いた語は、その語が原文で最初に現れたセグメントの行に書く。出どころ（原文から移動／一般知識で補足）を付ける
- `<draft>`: 改善案の本文のみ（Phase 3の生成規則に従う）。方針の説明や注記は含めない。補足マーカーも埋め込まない
- `<unresolved>`: 迷った箇所を1件ずつ、原文の引用・迷った点・採用した既定の判断の3点で書く。1件もなければ `なし` とだけ書く

## 全体の流れ

1. **入力の読み取り** — 対象文書・想定読者・追加制約を受け取る
2. **文書の分析** — セグメント分割と分類、主張の依存関係、用語の定義、表記ゆらぎを洗い出す
3. **追加制約の適用と改善案の生成** — 制約を反映し、2視点のルールに沿って改善案を生成する
4. **出力** — `<plan>` `<draft>` `<unresolved>` を返す

## Phase 1: 入力の読み取り

- 文書テキストが渡されていればそれを使う。ファイルパスが渡されていれば読み込む（読み取りのみ）
- 対象文書が渡されていない場合は、質問せず、処理を行わずにその旨だけを返す
- 想定読者が渡されていなければ、Phase 2-5で推定する
- 追加制約があれば、各制約の引用を原文中の該当箇所に対応づけておく（Phase 3で使う）

## Phase 2: 文書の分析

### 2-1. セグメント分割

- 文書を意味のまとまり（章・節・段落、または箇条書きの1項目など）単位でセグメントに分ける
- 分割の粒度は文書構造に従う。目安がなければ見出し／改段落／箇条書き項目を境界とする
- 1つのまとまりの中に性質の異なる内容（例: 手順の説明文とその理由づけ）が混在する場合は、文・節単位まで
  細分化してから個別に分類する（2-4節「理由づけの付いた手順」参照）
- 文書が長大な場合は、まず文書全体を1回走査して、結論・用語・依存順を決める。そのあと章・セクション単位で
  書き直す。章単位で処理したことを、`<plan>` の該当行の方針に明記する。ユーザーには確認しない

### 2-2. セグメントごとの分類

各セグメントを以下のいずれかに分類する。

- **論証型**: 主張と、それを支える理由・根拠の関係がある箇所
- **非論証型**: 手順（時系列の一連の操作）、時系列の出来事の記述、箇条書きの事実の列挙、描写・物語など、
  支持関係を持たない箇所。順序や網羅性そのものに意味がある

判定に迷う場合の目安（両方に当てて考える）:

- 「この文を削除したら、他の文の説得力が落ちるか？」→ Yesなら論証型
- 「この文の順番を入れ替えると、意味が変わるか？」→ 変わる（時系列・手順性がある）なら非論証型寄り

分類が一意に決まらないセグメントは、**非論証型として処理する**（並べ替えない側の扱い）。判定根拠を
`<unresolved>` に載せる。

文書全体が一方の型だけで構成される場合もある。その場合は、該当しない型の処理を単純にスキップしてよい。

### 2-3. 論証型セグメントの分析

1. セグメント内の主張を、文単位で洗い出す
2. 各主張について、その主張が成り立つために先に述べるべき主張（前提）を特定する
3. 前提が結論より先になる順に、主張の並びを決める（これを依存順と呼ぶ）
    - 依存関係が循環していて順序が決まらない場合は、並べ替えず原文の順を保つ。`<unresolved>` に載せる
4. 文書の結論を特定する。文書の結論とは、他のどの主張の前提にもならず、文書全体の最終的な主張となるものである
    - 結論が文書内に存在しない場合は、結論を作文しない。先頭へ移す処理も行わず、`<unresolved>` に載せる
    - 独立した最終的な主張が複数あり、一意に決まらない場合も同様に、先頭へ移さず `<unresolved>` に載せる
5. 複数の主張が合わさって初めて次の主張を支える場合は、それらを1つのまとまりとして扱う
    - まとまりの中の主張は、1つでも欠けると次の主張を支えられない
    - Phase 3では、まとまりを親項目の下位の箇条書きにして示す

### 2-4. 非論証型セグメントの分析

1. セグメント内の項目（文・ステップ・列挙要素）を、原文の順序どおりに洗い出す
2. 項目の種類を識別する
    - **手順**: 時系列の一連の操作。順序が依存関係そのものである
    - **時系列**: 日時と出来事の記述
    - **列挙**: 互いに独立した事実や規則の並び
3. 並べ替えない。原文の順序を保持する
4. 手順のステップに理由づけが付随している場合は、理由部分をそのステップの下位の項目として扱う
    （例:「ログを削除する。容量を圧迫するため」→ ステップの下位に理由を置く）。理由は削除しない

### 2-5. 用語の洗い出しと定義

1. 文書中のキーワードを洗い出す。キーワードには、名詞だけでなく「修飾語＋名詞」の形も含む
2. 想定読者の語彙にない語を特定する。想定読者が未指定なら、ここで文書の分野・文体・既出の語から読者像を推定する
3. 想定読者の語彙にない語ごとに、定義の出どころを次のとおり決める
    - 原文に定義がある: 原文の定義を使う（Phase 3で、初出の前へ移す）
    - 原文に定義がなく、広く確立した定義を持つ語（公的な規格・標準的な技術用語など）: 一般知識で定義を補う
    - 原文に定義がなく、文書固有の語（社内用語・独自の略語・プロジェクト名など）: 定義を補わない。`<unresolved>` に載せる
4. 具体例は、原文にあればそれを使う。原文になければ、定義から一意に作れる場合だけ補う
5. 定義文の中に想定読者の語彙にない語があれば、その語についても3〜4を繰り返す。想定読者の語彙だけになるまで続ける
    - 定義が循環して終わらない場合は、そこで止める。`<unresolved>` に載せる

### 2-6. 表記ゆらぎの洗い出し

1. 同じ概念を指すと見られる、表記の異なるキーワードの組を洗い出す（例:「利用者」と「ユーザー」）
2. 同じ概念だと断定できる組は、統一先を次の順で決める
    - 原文に定義がある語の表記
    - 文書内の最頻出の表記
    - 同数なら、初出の表記
3. 同じ概念だと断定できない組は、統一しない。両方そのまま残し、`<unresolved>` に載せる

## Phase 3: 追加制約の適用と改善案の生成

### 3-1. 追加制約の適用

追加制約が渡されている場合、Phase 2の判定に反映してから改善案を生成する。各制約の引用が指す原文の箇所を特定し、
次のように扱う。

- 用語の定義の提供: その定義を使う。一般知識で補う予定だった定義も、渡された定義を優先する
- 表記の統一先の指定: 指定された表記に統一する
- 並べ替えないでほしい箇所: その箇所は原文の順を保つ
- 分割しないでほしい文: その文は分割しない。文字数の上限を超える場合でも、そのまま残す
- 文書全体への要望（引用が空）: 全セグメントの判定に反映する

次の制約は**適用せず**、原文を変えない側で処理して `<unresolved>` に載せる。

- 引用が原文のどこを指すか一意に定まらない（最も近い箇所へのマッピングを試みても決まらない）
- 原文の内容の削除を求めている
- 他の制約と矛盾している

### 3-2. 改善案の生成

2視点のルールに沿って、原文の内容を並べ替え・分割・統一・構造化し、必要な定義を足した本文を生成する。原文の言い回しは、
このPhaseの規則で必要な範囲を超えて変えない。

#### 意味論の読みやすさ

1. **文書の結論を先頭に置く**。他の主張の依存順（Phase 2-3）の例外として、結論の文は文書の先頭に移す
    - 結論は `- 結論: 〜` の形で書く
    - 結論の文だけを文単位で元のセグメントから切り出す。見出しは、所属するセグメントと一緒に動く
    - 結論を導く論証型セグメントの末尾に、`以上より、冒頭の結論が成り立つ。` と1文で締める
2. **結論で使う語の定義だけを、結論の直前に置く**。想定読者の語彙にない語がある場合に限る
    - 結論より前に置く定義は、結論で使う語の分だけにする。ほかの語の定義は、手順3で置く
3. **用語は、初出の前に定義する**。想定読者の語彙にない語の定義（と、可能なら具体例）を、改善案の中でその語が最初に
   現れる位置の直前に置く
    - 「初出」は改善案の並び順で判定する。原文の並び順ではない
    - 定義文の中の語にも同じ規則を適用する（Phase 2-5の5）
    - 定義は次の形で書く。定義文と具体例は、別々の単文の項目にする

```
- 用語「冪等性」
    - 同じ操作を何度行っても、結果が1回の場合と変わらない性質である。
    - 例: ユーザーの削除を2回行っても、結果は同じである。
```

4. **主張は依存順に並べる**。論証型セグメントでは、前提が結論より先に来る順に並べる
    - セグメント内は、文単位で依存順に並べ直す
    - セグメント間も、依存順に並べ直す。並べ替えの単位はセグメントである。結論と定義だけが例外で、文単位で動かす
    - 非論証型セグメントは、原文の順序を保つ
5. **並べ替えられない箇所は、原文の順を保つ**。循環依存、文単位の越境が必要な場合などである。`<unresolved>` に載せる

#### 記号的な読みやすさ

1. **キーワードの表記を統一する**。統一先は、Phase 2-6で決めたものを使う。統一しないと決めた組は、そのまま残す
2. **全ての文を単文にする**。1つの文に述語は1つだけにする
    - 複文は、複数の単文に分ける
    - 分けるときは、主語と接続語を補ってよい。接続語は「そのため」「しかし」などで、論理関係を残す。新しい主張は足さない
3. **一文を50文字以内にする**。超える文は分割する
    - 次のものは文字数に数えない: コード・コマンド・URL、引用、分割できない固有名詞
    - 例外のために50文字を超える場合は、そのまま許容する
4. **箇条書きと階層で構造化する**
    - 本文は箇条書きにする
    - 複数の主張が合わさって次の主張を支える場合は、そのまとまりを親項目の下位の箇条書きにする（Phase 2-3の5）
    - 補足・定義・具体例は、対象の項目の下位の箇条書きにする
    - 原文の見出しは、所属するセグメントとともに残す
5. **手順は番号付き箇条書きにする**。時系列と列挙は、番号なしの箇条書きにする
    - 時系列は、日時を各項目の先頭に置く
    - 手順に付随する理由づけは、そのステップの下位の番号なしの箇条書きにする

## エッジケース対応

- **対象文書が渡されていない**: 質問せず、処理を行わずにその旨だけを返す
- **想定読者が渡されていない**: 文書から推定し、推定した読者像を `[全体]` 行に書く。推定の根拠を `<unresolved>` に載せる
- **文書の結論が存在しない／一意に決まらない**: 結論を作文せず、先頭へ移さない。`<unresolved>` に載せる
- **手順・列挙だけで結論を持たない文書**: 「結論を先頭に置く」ルールを適用しない。それ以外のルールは適用する
- **文書固有の語で、原文に定義がない**: 定義を補わず、`<unresolved>` に載せる
- **定義が循環する**: 循環した箇所で止め、`<unresolved>` に載せる
- **同じ概念か断定できない表記の組**: 統一せず両方残し、`<unresolved>` に載せる
- **依存関係が循環する／文単位の越境が必要**: 並べ替えず原文の順を保ち、`<unresolved>` に載せる
- **セグメントが論証型／非論証型のどちらか一意に決まらない**: 非論証型として処理し、判定根拠を `<unresolved>` に載せる
- **1つのまとまりに論証的要素と非論証的要素が混在する**: 文単位でセグメントをさらに分割するか、手順に付随する理由づけとして
  扱う。どちらにしたかを `<unresolved>` に載せる
- **文章が長大**: 文書全体の1回目の走査で結論・用語・依存順を決めてから、章・セクション単位で書き直す。確認はせず、
  `<plan>` に明記する
- **原文の内容の削除を求める制約**: 適用せず、`<unresolved>` に載せる
- **制約の引用が原文のどの箇所を指すか一意に定まらない**: 最も近い箇所へのマッピングを試み、定まらなければ適用せず
  `<unresolved>` に載せる
- **ユーザーへの質問・確認・元の文章への書き込み**: 行わない。確認が必要な事柄はすべて `<unresolved>` で呼び出し側に返す
