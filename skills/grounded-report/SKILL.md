# Grounded Report — 根拠に基づく自己検証型HTMLレポート生成

ユーザーが指定した目的を満たすレポートを、根拠資料を伴う形で生成し、5つの品質要件を独立した検証者が
自動判定するループ（実行→検証→修正）を基準を満たすまで自律的に繰り返すスキル。ループの構造は
[[setup-loop]] が教える「実行・検証・終了条件」の手法に基づくが、実行手順・検証軸・終了条件は
このスキル自体にあらかじめ固定で組み込まれているため、都度のインタビューは行わない。

## 全体の流れ

1. **入力の受け取り**（ユーザーとの対話）— 目的・対象読者・根拠資料の指定・出力先を確認する
2. **実行計画の提示と承認**（ユーザーとの対話）— 固定の実行・検証・終了条件をユーザーに提示し、明示的な承認を得る
3. **事前準備**（Coding Agentが実施）— WebSearch/WebFetch等の必要な権限を前倒しで確認する
4. **ループの実行**（Coding Agentが自律実行）— 調査→執筆/修正→独立検証→判定を終了条件まで繰り返す
5. **完了報告**（Coding Agentが実施）— 成果物のパスと検証結果、または残課題を報告する

## Phase 1: 入力の受け取り

以下をユーザーに確認する。依頼内容から自明な項目は確認のみに留める。

- **目的（必須）**: このレポートで何を達成したいか。曖昧な場合は深掘りして具体化する
- **対象読者（任意）**: 属性（例:「エンジニア向け」）に加えて、「知っている前提でよい用語・概念」を
  自由記述で軽く例示してもらう（依頼内容から自明な場合は確認のみに留める）。未指定の場合は「特に指定が
  なければ、専門知識のない一般読者向けとして進めますがよいですか」と一言確認したうえで、「当該分野の
  専門知識を持たない一般読者（分野固有語はすべて未知として扱う）」を既定値とする。ここで確認した内容は、
  Phase 4の用語選別・用語定義検証者の判定基準として用いる
- **根拠資料の指定（任意）**: 使ってほしい特定の資料（URL・ファイル）や、優先・除外したいMCP検索ソース
  （例: 社内Wiki検索、特定のドキュメント検索MCP等）があれば受け取る。未指定ならPhase 4の調査ステップで、
  Web検索に加えて動的に検出した検索系MCPツール（判定基準は「検索系MCPツールの判定基準」を参照）を用いて
  自律的に収集する
- **出力先パス（任意）**: 未指定の場合はファイル名を提案し（例: 目的をスラグ化した `<slug>-report.html`）、
  保存先をユーザーに確認する

## Phase 2: 実行計画の提示と承認

実行計画の提示に先立ち、接続中のMCPツールの中から検索系とみなせるものを動的に検出する（判定基準は
「検索系MCPツールの判定基準」を参照）。以下を含む実行計画をユーザーに提示し、明示的な承認を得てから
Phase 3に進む（承認前にPhase 4を開始しない）。

- **実行手順**: Phase 4で説明する1イテレーションの内容（調査→執筆/修正）
- **検証手順**: Phase 4で説明する5体の独立した検証者と、それぞれの合格基準
- **終了条件**: 5検証者すべてが合格した時点でループを終了する。最大イテレーション数は10回。上限到達時は
  ループを中断し、現状のレポートと残課題を提示する
- **必要な権限**: WebSearch・WebFetch（実行フェーズでの資料収集、および検証フェーズでの引用元照合に使用する。
  必須）。加えて、動的検出した検索系MCPツールがあればその名前を列挙する（1つも検出されなければその旨を伝え、
  Webのみで進める）

## 検索系MCPツールの判定基準

接続中のMCPツールから、読み取り専用でレポート作成に使える「検索系」のものを動的に検出する。特定の
ツール名・サーバー名を決め打ちしない。

- ツールのアノテーション（`readOnlyHint`等、読み取り専用を示すメタデータ）があれば、それを最優先の
  判定根拠とする
- アノテーションが無い場合は、ツール名・説明文のキーワードで判定する: search/query/find/検索/一覧/取得
  等の語を含み、かつcreate/update/delete/write/送信/削除/作成/更新等の副作用を示唆する語を含まないものを
  検索系とみなす
- 両方の語を含む、または説明文が不十分で判定できないツールは対象から除外する（安全側に倒す）
- Phase 1でユーザーが除外・優先を指定した場合はそれを優先する
- 検索系MCPツールが1つも見つからない場合は、WebSearch/WebFetchのみで進める（後続フローに影響しない）

## Phase 3: 事前準備

Phase 2で承認された計画をもとに、ループが承認待ちで中断しないよう、WebSearch・WebFetchおよびPhase 2で
承認された検索系MCPツールを一度実行（または安全な形で試行）して事前に承認を得ておく。

## Phase 4: ループの実行

終了条件を満たすまで、以下を1イテレーションとして繰り返す。ループ実行中はユーザーの確認を求めずに
自律的に処理し続ける。

### 4-1. 調査

- 初回イテレーション: 目的に関連する**一次情報・高信頼のソース**（公式ドキュメント、査読済み論文、公式統計など）を
  WebSearch・WebFetch、および利用可能な検索系MCPツールで収集する。ユーザー指定の資料があればそれを優先的に
  用いる。情報源の信頼度は出典の種別（Web/MCP）で機械的に判断せず、Web由来と同じ基準（一次情報か・当事者性が
  高いか）で個別に判断する
- 同一の論点についてWeb由来とMCP由来の情報が食い違う場合、出所ではなく、より一次情報・当事者性に近い方を
  優先する
- 2回目以降: 直前の検証（特に「引用存在検証者」「引用整合性検証者」）で不足・不整合を指摘された論点についてのみ
  追加調査を行う
- 収集した資料は、出典名・取得日時とともに記録する（参考文献一覧の元データになる）。Web由来はURLを、
  MCP由来は取得に使ったツール名と検索クエリ/パラメータ（deeplinkやリソースID等URL相当のものが取得できれば
  それも）を記録する

### 4-2. 執筆・修正

収集した資料を根拠に、Phase 1で確認した目的・対象読者に沿ってHTMLレポートを執筆（1回目）または直前の
検証者の指摘を踏まえて修正（2回目以降）する。出力仕様は後述の「出力仕様」に従う。

### 4-3. 検証

5体の独立した検証者を `Agent` ツールでサブエージェントとして起動する（並列実行可）。各検証者には
**レポート本文（HTMLファイルの内容）と、その検証者固有の判定基準のみ**を渡し、どう執筆・修正したかという
実装文脈は一切渡さない（ただし用語定義検証者にのみ、Phase 1で確認した対象読者の前提知識を判定基準の
一部として追加で渡す。他4検証者には渡さない）。引用整合性検証者にのみ、WebFetchおよびPhase 3で承認済みの
検索系MCPツールを呼び出せるサブエージェントとして起動する（他4検証者には検索・取得系ツールへのアクセスを
与えない）。各検証者の判定基準は後述の「検証者への指示」を参照する。

### 4-4. 判定

- **5体すべて合格** → ループを終了し、Phase 5へ進む
- **一部不合格** → 各検証者が指摘した該当箇所・理由を集約し、次のイテレーションの執筆・修正（4-1・4-2）に反映する
- **最大イテレーション数（10回）に到達** → ループを中断し、Phase 5で現状のレポートと残課題を報告する

各イテレーションの終わりに「イテレーション番号 / 実施内容 / 各検証者の合否」を1〜2行でユーザーに報告する。

## Phase 5: 完了報告

- 終了条件を満たした場合: 成果物のファイルパスと、各検証者が最終的に合格と判定したことを報告する
- 上限到達で中断した場合: 現状のファイルパスと、各検証者が残した指摘（未解決の項目）を一覧で報告する

## 出力仕様（HTMLレポート）

- **形式**: 単一の自己完結HTMLファイル。外部ライブラリ・CDNへの依存を持たない（オフラインでも常に正しく
  表示されるようにするため）
- **構成**: タイトル、本文（セクション見出し）、参考文献一覧（脚注番号順）
- **図解**: インラインSVGで描画する（外部の描画ライブラリを`<script>`で読み込まない）
  - 各セクション（主張のまとまり）ごとに、そのセクションの論証構造（前提→中間結論→最終結論の関係）を
    可視化した**論証図を必須で含める**
  - 内容の理解を助ける自由形式の図解（フローチャート・概念図など）を、必要に応じて追加してよい
- **用語**: 本文中で初めて使う分野固有語のうち、Phase 1で確認した対象読者の前提知識に照らして読者が
  知らない可能性が高いものについて、その直前または直後に定義・背景解説（どのような文脈・背景を持つ
  言葉か）を置く。可能であれば具体例も添える（具体例は任意）。対象読者が既定値（専門知識を持たない
  一般読者）の場合は、分野固有語はすべて未知として扱う
- **引用**: 主張の根拠となる外部資料には脚注番号（例: `[1]`）を本文に付け、文末に参考文献一覧を置く。
  各出典は出典名・取得日時とともに、URL（またはMCP経由でdeeplink/リソースID等URL相当のものが取得できる
  場合はそれ）を記載する。URL相当のものが存在しない出典（MCP検索結果など）は、取得元のMCPツール名・
  検索クエリ/パラメータ・取得日時を記載する

## 検証者への指示

各検証者は独立したサブエージェントとして起動し、レポート本文と以下の合格基準のみを渡す。ただし
用語定義検証者にのみ、Phase 1で確認した対象読者の前提知識（属性および「知っている前提でよい用語・
概念」）を判定基準に付記して追加で渡す。

1. **用語定義検証者**: 本文中に現れる分野固有語のうち、渡された対象読者の前提知識に照らして読者が
   知らない可能性が高いものについて、初出前に定義・背景解説があるか確認する。対象読者が既定値
   （専門知識を持たない一般読者）の場合は、分野固有語はすべて未知として扱う。具体例の有無は合否に
   影響しない。定義・背景が欠けている用語があれば、すべてリストアップして報告する
2. **目的達成検証者**: ユーザーが指定した目的（Phase 1で確認した内容）を、このレポートが果たしていると
   判定できるか確認する。果たしていない場合、不足している観点を具体的に指摘する
3. **論理構成検証者**: 本文と各セクションの論証図を読み、主張の論理構成が演繹的に妥当であるか、または
   十分に確度の高い帰納的推論であるかを判定する。論証図が本文の論理構造と矛盾していないかも確認する。
   飛躍のある推論・支持の弱い結論があれば該当箇所を指摘する
4. **引用存在検証者**: 本文中の主張（特に事実主張・データ）に脚注番号による引用が付与されているか確認する。
   図解内のキャプション・数値も検証対象に含める。引用のない主張があれば該当箇所を指摘する
5. **引用整合性検証者**: 参考文献一覧に列挙された各出典を、Web出典はWebFetchで、MCP経由の出典は記録された
   取得元ツール名・検索クエリ/パラメータを使って同じMCPツールで実際に再取得し、本文および図解の主張が
   出典の記載内容から飛躍せずに導けるかを照合する。出典に記載のない内容の付加・誇張・逆の解釈があれば、
   該当箇所と出典側の該当箇所を対比して指摘する。再取得に失敗した出典（MCPツールの呼び出しエラー等）は
   その旨を明示し、根拠不十分として指摘する

## エッジケース対応

- **信頼できる一次情報が見つからない論点がある**: 無理に執筆を進めず、見つからなかった論点をユーザーに
  報告し、目的の見直しや資料の追加提供を相談する
- **検証者間で指摘が競合する**（例: 引用整合性は問題ないが目的達成検証者は根拠不足と指摘する）: 両方の
  指摘を次のイテレーションの修正に反映する。優先順位に迷う場合はユーザーが指定した目的の達成を最優先する
- **Phase 2の承認前**: 実行・検証を開始しない
- **出力先に既存ファイルがある**: 上書きしてよいかユーザーに確認する
- **検索系MCPツールが1つも検出できない、または承認済みMCPツールの呼び出しがすべて失敗する**: WebSearch・
  WebFetchのみで調査・検証を継続する。完了報告でその旨を明示する
