# boiling-docs-core テスト

boiling-docs-core が文書を読みやすく書き直したあとも**内容を落としていないか**、また**読みやすさのルールを満たしているか**を検証する。入力文書に埋め込んだ「アンカー語」が出力に残っているかを機械的に照合する。文字数や番号付き箇条書きなど、機械的に数えられるルールも照合する。コアは非対話なので、ユーザー承認を擬似化する指示は不要。

## 実行

```bash
tests/boiling-docs-core/run.sh                 # 全ケースを各3回実行
tests/boiling-docs-core/run.sh -n 5 01 06      # 実行回数を5回にし、01・06で始まるケースだけ実行
AGENT_CMD="<agent-cli>" tests/boiling-docs-core/run.sh
```

- `AGENT_CMD` は、**プロンプトを標準入力で受け取り、応答を標準出力に返す**コマンド（既定: `claude -p`）。Agent を差し替える箇所はここだけ
- プロンプトは `skills/boiling-docs-core/SKILL.md` の全文、対象文書、（あれば）想定読者と追加制約から組み立てる。Agent のスキル呼び出し機能には依存しない
- 1ケースにつき N 回（`-n`）実行する。ケースは直列に実行するため、全ケースで 18 × N 回 Agent を呼ぶ
- `maxlen` の照合に `python3` を使う。見つからない場合は終了コード 2 で止まる
- いずれかのケースが FAIL なら終了コード 1

## 生成文章の確認

出力は `tests/boiling-docs-core/out/<timestamp>/` に保存する（`tests/*/out/` は `.gitignore` 済みで、Git の記録には残らない）。

| ファイル | 内容 |
|---|---|
| `summary.tsv` | 全ケースの判定と、種別ごとの通過数/総数 |
| `<case>/report.md` | **読む用**。アンカーごとの ○/×、入力文書、想定読者、追加制約、期待値、生成文章（run ごと）を1ファイルに並べたもの。文字数の上限を超えた文があれば、生成文章の直後に列挙する |
| `<case>/run-N.md` | Agent の生の応答 |
| `<case>/run-N.draft.md` | 応答から抽出した改善案（`<draft>`。must / may / any / order / forbid / maxlen / numbered の照合対象） |
| `<case>/run-N.plan.md` | 応答から抽出した改善方針の概要（`<plan>`） |
| `<case>/run-N.unresolved.md` | 応答から抽出した未確定事項（`<unresolved>`。flag の照合対象） |
| `<case>/run-N.maxlen.txt` | 文字数の上限を超えた文（`maxlen` の違反。空なら違反なし） |
| `<case>/run-N.check` | 照合結果（TSV） |
| `<case>/run-N.err` | Agent コマンドの標準エラー |

機械照合では、言い換えによる意味の脱落や、「全て単文になっているか」「想定読者の推定が妥当か」「補った定義が正しいか」は検出できない。`report.md` の生成文章と `plan` を目視で確認すること。

## 判定

| 種別 | 扱い |
|---|---|
| `must` / `order` / `any` / `flag` / `forbid` / `maxlen` / `numbered` | 通過率が100%未満（N回のうち1回でも未通過）なら FAIL |
| `may` | 残存率の記録のみ。スキル改修前後の比較に使う |
| `format` | `<plan>`・`<draft>`・`<unresolved>` の3つをすべて応答から抽出できたか（記録のみ）。`<draft>` を抽出できない場合は応答全体で改善案の照合を行う |

## ケースの書き方

`cases/<番号>-<名前>/` に、次のファイルを置く。

- `input.md`: 入力文書。1ケースに1つの罠だけを仕込み、残すべき事実には**言い換えにくい固有の語**（コマンド、数値、固有名詞）を含める
- `expect.txt`: 期待値。1行1項目、`#` で始まる行はコメント
- `audience.txt`（任意）: 想定読者。自然文を1行以上書く。ファイルがなければ想定読者なしで呼び出す（コアが推定する）
- `constraints.txt`（任意）: 追加制約。1行1件、`「対象箇所の原文の引用」: 要望の自然文` の形。`#` で始まる行と空行は無視する。ファイルがなければ制約なしで呼び出す

```
must: --force                # 必ず残る。1回でも欠けたら FAIL
may:  ポート開放の理由         # 残らなくてもよい。残存率のみ記録
any:  案A | 案B | 案C         # 列挙のうち1つ以上が残る
order: step-a < step-b        # 最初の出現位置がこの順になる（`<` 区切りで連鎖可）
forbid: DB                    # 現れてはならない（表記ゆらぎの残存、作文された定義の検出）
maxlen: 50                    # すべての文が50文字以内。コード・URL・「」内の引用・見出しは数えない
numbered: 6                   # 番号付き箇条書き（"1. " など）の行が6行以上ある
flag: 90%                     # <unresolved> に現れる。迷うべき箇所を迷えているかの確認
```

アンカーは `must` / `may` / `any` / `order` / `forbid` では `<draft>` に、`flag` では `<unresolved>` に対する**部分文字列の一致**で判定する（大文字小文字・空白は区別する）。`forbid` は部分文字列なので、禁止したい語が別の語の一部として正当に現れないことを、入力文書の側で確かめておく。

結論の先頭配置と定義の先出しは、`order` で確かめる（結論の特徴語 < 前提の特徴語、定義の特徴語 < 結論の特徴語）。AI が補う定義の文面は予測できないため、定義の位置は、スキルが定める見出し `用語「語」` を目印に照合する。

## ケース一覧

| # | 種別 | 仕込んだ罠 |
|---|---|---|
| 01 | 手順 | 順序依存。順序が崩れると成立しない。番号付き箇条書きのまま残る |
| 02 | 手順 | 似ているが対象が違う2系統のステップ（重複として統合されてはならない） |
| 03 | 手順 | 実行に必須の数値・フラグが短い文に埋まっている |
| 04 | 列挙 | 先頭2項目の言い回しが近い。削除しないので両方残る |
| 05 | 時系列 | 日時と出来事の順序に意味がある。すべての項目が残る |
| 06 | 論証 | 結論が末尾にある。結論が先頭に移り、要件と GC 停止の2点を含む前提がすべて残る |
| 07 | 論証 | 独立した理由が4つ。削除しないのですべて残る |
| 08 | 論証 | 結論が末尾にある。事実 → 中間結論 → 最終結論の連鎖が、結論先頭・依存順で並ぶ |
| 09 | 混在 | 論証セグメントと手順セグメントが交互に並ぶ |
| 10 | ハイブリッド | 手順＋理由づけ（ステップも理由も削除されない） |
| 11 | 未確定事項 | 同じ概念か断定できない語（アラート／通知）。統一も削除もせず、`<unresolved>` に載せる |
| 12 | 追加制約 | 文書固有の語（Mochi）の定義を追加制約で渡す。渡された定義が初出の前に置かれる |
| 13 | 追加制約 | 内容の削除を求める制約（適用せず `<unresolved>` に載せる） |
| 14 | 用語 | 文書固有の語（Mochi）で、原文に定義がない。定義を作文せず `<unresolved>` に載せる |
| 15 | 用語 | 末尾にある原文の定義が、結論の前に移る |
| 16 | 用語 | 原文に定義がない広く確立した用語（冪等性）。一般知識で定義を補い、結論の直前に置く |
| 17 | 表記 | 「データベース」と「DB」が混在する。最頻出の表記に統一される |
| 18 | 複文・長文 | 複文と長い一文が単文に分かれ、どの文も50文字以内になる |

すべてのケースは、実在の Agent で通過率を測って期待値を調整する前の初期案である。特に `maxlen`（50文字）は、Agent が文字数を数え誤る場合があるため、通過率を見て扱いを決める。

## 範囲外

対話skill `boiling-docs` のテストは、このテストの対象外。ソース種別（ファイル、MCP、テキスト）ごとの Phase 5 の分岐、未確定事項を1件ずつ質問する流れ、要望対応でコアを再呼び出しして Phase 3 に戻る経路、コアが見つからない場合の中断は検証しない。
